# AI 与大数据招聘能力地图

> 本目录现有的核心资料是 [ADB 命令控制安卓机器人设备指南](adb命令控制安卓机器人设备指南.md)。它覆盖设备连接、应用管理、交互、日志、截图录屏、设备信息和恢复相关操作。它能支持“端侧联调、设备自动化、数据采集/问题取证”的辅助能力，**不是** Android 原生开发、算法工程或大数据计算的核心证据。

## 一、岗位定位：辅助能力如何服务 AI 与数据工作

| 岗位方向 | 关联程度 | 可以说明的价值 | 不能据此声称的能力 |
| --- | --- | --- | --- |
| AI 应用工程师（移动端协作） | 中 | 协助验证模型/接口在真机上的输入、权限、网络、日志和异常表现 | 不等于会 Android 架构、Jetpack Compose 或端侧模型部署 |
| 移动端测试 / 自动化测试工程师 | 高 | ADB 多设备控制、安装启动、交互、日志、截图录屏和问题取证 | 不等于已建立成熟测试框架或完整 CI 平台 |
| IoT / 机器人 / 边缘设备联调工程师 | 中高 | 设备连接、序列号定位、应用/服务启动、系统资源和网络检查 | 不等于具备硬件驱动、固件或嵌入式算法开发经验 |
| 数据采集与质量工程师 | 中 | 用受控设备执行固定步骤，生成可复现的日志、截图、性能/行为证据 | 不等于拥有生产埋点平台或大规模数据采集经验 |
| 大数据 / 模型工程师 | 低（差异化辅助） | 理解端侧数据如何产生、被授权、脱敏和验证 | 不替代 SQL、Flink、数仓、训练、特征工程和模型评估能力 |

最好的简历策略是把它放在“**端到端 AI 应用交付的真机验证和数据质量意识**”一栏，而不是将 ADB 命令写成核心算法或大数据能力。

## 二、从现有资料抽取的技能树

```text

│  ├─ adb server、USB / 无线连接、授权状态
│  ├─ adb devices 与多设备 -s 序列号
│  └─ 设备型号、系统版本、网络和硬件信息
├─ 应用生命周期
│  ├─ 查看包名、安装、卸载、清数据、安装路径
│  ├─ 启动/停止应用、Activity、Service、广播
│  └─ 进程、前台页面、应用详情和内存状态
├─ 自动化交互
│  ├─ input 文本、点击、滑动、按键、解锁
│  ├─ 截图、录屏、文件 pull/push
│  └─ Monkey 压力测试的基础入口
├─ 诊断与可观测性
│  ├─ logcat 级别/Tag/格式/时间范围过滤
│  ├─ 内核日志、CPU、内存、电池、网络信息
│  └─ 复现步骤、设备信息和证据的关联
├─ 风险控制
│  ├─ root、SELinux、dm-verity、Recovery/Fastboot/sideload
│  ├─ 清数据、系统设置和刷机的可恢复边界
│  └─ 设备标识、截图、日志和应用数据的脱敏
└─ 需补强的专业能力
   ├─ Android SDK、Kotlin/Java、Gradle、Jetpack 与原生应用代码
   ├─ Appium/UIAutomator/Espresso 等自动化框架
   ├─ 设备农场、CI、报告平台和测试数据治理

```

目录中的指南已覆盖多设备指定、Activity/Service、`logcat` 过滤、截图录屏、CPU/内存和网络信息。这些内容的招聘价值在于：遇到“模型接口在手机上表现异常”时，能先固定设备和应用版本，再保存可复现的证据，而不是只说“我这里复现不了”。

| --- | --- | --- | --- |

| 问题取证 | 同一指南中的 logcat、截图录屏、进程/资源章节 | 如何让日志时间、设备状态、操作步骤和截图可以关联？ | 匿名日志片段、录屏、复现时间线 |

## 四、可交付实战项目

### 项目一：多设备 AI 应用联调与证据采集脚本

**场景：**一个移动端 AI/数据应用调用后端接口或展示模型结果时，需要在多台测试机上安装、启动、执行固定流程并保存失败证据。项目只调用正常调试/测试命令，不使用 root 或系统绕过能力。

```text
设备清单（已授权）
  → 指定 adb -s <serial>
  → 安装/启动测试 APK
  → 输入、点击、滑动完成固定场景
  → 截图/录屏 + 过滤 logcat
  → pull 到本地证据目录
  → 输出设备—应用—时间—结果清单
```

**应交付：**

- 一个参数化脚本：必须显式传入设备序列号、包名、APK 路径和输出目录，拒绝“默认操作第一台设备”。
- 测试场景说明：启动、网络断开/恢复、空输入、接口超时、重复提交、前后台切换等步骤。
- 证据命名规范：`时间-设备别名-应用版本-场景-结果`，可关联截图、录屏、日志和命令输出。
- 日志脱敏规则：过滤 Token、手机号、用户 ID、定位、文件路径和模型请求正文；仅保留排查必需字段。
- 一份失败复盘模板：设备、系统、应用版本、复现概率、操作时间线、关键 logcat、服务请求 ID（如有）和恢复方式。

**验收点：**多设备并发/轮流执行时不会串设备；失败时能从一份证据包复现问题；脚本不会执行清空数据、卸载、刷机等破坏性操作，除非使用者明确传入确认参数。

### 项目二：端侧数据采集链路的隐私与质量检查

**场景：**为一个需要从 Android 端收集匿名事件/性能信息的 AI 应用设计测试闭环，确认“采集到的数据能用”而不是只确认“客户端发出了请求”。

**应交付：**

- 事件 schema：事件名、匿名设备别名/会话 ID、事件时间、应用版本、网络类型、耗时、状态码；明确禁止采集 IMEI、Android ID、通讯录、原始用户文本等非必要信息。
- 采集前检查：权限、网络、时间同步、应用版本、用户同意/测试授权和字段开关。
- ADB 辅助验证：使用 logcat 和网络/进程信息核实事件是否触发，截图保存页面状态；不从设备导出敏感应用数据库。
- 数据质量规则：必填字段、时间单调性、事件去重键、版本分布、异常耗时、采样率和日志延迟。
- 后端/数仓对账表：设备端触发次数、服务端接收次数、落库次数和分析结果之间的差异归因。

这项交付将端侧能力连接到数据工程，但核心仍是数据契约和隐私治理。只有完成后端/数仓校验，才能说明端到端采集质量，不应只展示 ADB 截图。

### 项目三：端侧模型/接口异常的最小复现包

**场景：**当某台手机上的 AI 接口、推荐结果或图像/时序输入异常，建立一个可交给后端、算法和测试同事共同定位的复现包。

**应交付：**

- 复现条件：机型、Android 版本、应用版本、网络、权限、页面路径、输入类型与预期行为。
- 操作录像/截图、经过过滤的 logcat、CPU/内存、前后台状态和时间窗口。
- 分层排查结论：客户端 UI/权限、网络、接口响应、后端日志、模型服务五层中哪些已证实、哪些待验证。
- 不确定性说明：端侧看到的展示异常不能直接推断为模型算法问题，必须有请求/响应和服务端证据。

## 六、面试要点：至少回答好这些问题

1. **多设备调试为什么必须指定序列号？**
   - 默认目标可能不确定；安装、清数据或启动命令作用到错误设备会污染测试和证据。
2. **如何把一个手机问题变成可复现缺陷？**
   - 固定设备/系统/应用/网络版本，记录步骤和时间，保存截图录屏、过滤日志、预期/实际结果和恢复方式。
3. **`logcat` 如何避免“日志很多但没有证据”？**
   - 以包名/Tag/级别/时间范围过滤，并让日志时间与操作步骤、请求 ID、截图关联；不要直接导出全量敏感日志。
4. **为什么不应随意使用 root、清数据或刷机命令？**
   - 这些会改变系统或应用状态、影响证据完整性并带来安全/恢复风险，应先做可逆观察和备份。
5. **端侧采集数据怎样保护隐私？**
   - 最小化字段、获得授权、使用匿名标识、脱敏日志/截图、控制保留和访问；不采集不必要的稳定设备标识。
6. **如何判断 AI 结果异常来自客户端、网络还是模型？**
   - 先核对输入、权限、页面/版本、网络和接口响应；再关联后端和模型日志，不能由 UI 表象直接归因。
7. **端侧与数仓对账的常见差异原因？**
   - 网络失败/重试、离线缓存、重复投递、时钟偏差、采样、隐私开关、服务端丢弃和落库延迟都可能导致差异。

## 七、AI 协作方式：提高脚本和分析效率，同时守住设备边界

AI 可以帮助生成参数校验充分的 ADB 脚本草案、从脱敏日志中归类错误、整理复现步骤、生成测试矩阵和把截图/日志说明转换为缺陷模板。人工必须确认目标设备、授权、包名、危险命令、日志脱敏与最终故障归因。

```text
请协助生成“只读或可逆”的 ADB 联调方案。
设备：已授权测试机，别名=<alias>；应用包名=<package>；场景=<步骤>；
需要证据=<截图/录屏/过滤日志/资源信息>。
限制：每条命令必须显式使用 -s；不得 root、刷机、读取账号/密码、
导出 IMEI/Android ID/应用私有数据，也不得清数据或卸载。
请先给出命令清单、失败分支、脱敏点和人工确认项。
```

如果 AI 建议了未在本目录验证的系统级命令，先停在测试机和官方文档核实；模型生成的 Shell 命令尤其不能直接复制到连接中的设备执行。

## 八、现有资料缺口与下一步

| 缺口 | 对求职的影响 | 建议补齐方式 |
| --- | --- | --- |
| 只有 ADB 操作指南，没有 Android 源码项目 | 不能证明原生开发能力 | 建一个最小 Kotlin/Java Demo，明确 API、日志和测试入口 |
| 缺少 Appium/UIAutomator/Espresso 等自动化框架 | 脚本自动化的可维护性不足 | 选择一个框架，完成页面对象、报告和 CI 触发的样例 |
| 缺少端到端采集和数仓对账代码 | 难以证明“设备数据”进入平台后的质量 | 用匿名事件实现端侧—接口—表/看板的最小对账 |
| 缺少端侧模型部署/性能证据 | AI 端侧岗位会追问推理框架和性能 | 若目标岗位需要，再补量化、冷启动、内存、耗电和隐私测试；不需要则不硬凑 |
| 高风险命令混在参考资料中 | 容易被误解为可直接用于生产/他人设备 | 在后续脚本中默认禁用破坏性操作，单独记录授权和恢复方案 |

## 九、投递前自查

- 能说明这部分是端侧联调/测试辅助能力，而不是取代 AI/大数据核心栈。
- 有一份脱敏且可复现的脚本、日志证据包或缺陷报告。
- 所有设备操作均有授权，所有标识、截图和日志均完成脱敏。
- 能讲清从“手机点击”到“服务端/数仓记录”的验证断点和责任边界。
- 不在简历或作品集中展示 root 绕过、安全绕过、Wi-Fi 密码、设备 ID 或高风险刷机操作。
