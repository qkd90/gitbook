# 数据库和中间件：AI 与大数据招聘能力地图

## 使用范围

本页基于目录中已有的 SQL、MySQL、MongoDB、Elasticsearch、Kafka、Doris、Nginx、导入导出和监控资料，整理 AI 应用、大数据研发和后端平台岗位所需的数据能力。

目标不是“会安装很多组件”，而是能从业务口径、数据模型、读写链路、性能、可靠性和运维证据六个维度解释选择与风险。

## 岗位关联

### AI 应用与数据产品

- AI 应用需要可靠保存任务、会话、文档元数据、反馈和审计信息。关系型数据库、文档数据库和搜索引擎的适用边界决定系统是否可维护。
- 模型输出或检索结果并不天然可信；候选人应能说明来源数据、版本、时间边界、权限过滤和查询口径，而不是只谈向量或模型名称。
- Kafka 可以承接异步事件，Doris 可承接分析查询，Elasticsearch 可承接检索，MongoDB 可承接灵活文档；是否选择它们必须回到读写模式和一致性要求。

### 大数据研发

- 大数据岗位的核心不只是计算框架，还包括 SQL 正确性、分区/窗口思维、数据建模、数据质量、消息链路和 OLAP 查询。
- 本目录的行业 SQL 题、Partition By、Doris、Kafka、MySQL 设计与监控资料可用于展示从单条查询到数据链路诊断的基本能力。
- 面试时要能区分事务库、分析库、搜索库和消息系统的职责，避免将所有问题都用某一种存储解决。

### 后端平台

- 后端平台需要在数据正确、请求性能、操作安全和故障可恢复之间取舍。表设计、索引、监控、主从、导入导出与 Nginx 资料形成这条链路。
- 数据修复、批量更新、同步消费和搜索索引异常都可能扩大影响面。平台工程师的能力体现在先检查、最小变更、再验证，而不是只会执行命令。

## 能力分层与证据

| 层级 | 需要回答的问题 | 本目录对应基础 | 可验证证据 |
| --- | --- | --- | --- |
| L1 SQL 语义 | 查询是否按正确粒度、关联和时间边界计算 | SQL 题库、窗口函数、行业场景题 | SQL、样例数据、预期结果和反例 |
| L2 数据模型 | 表、主键、字段、字符集和索引为什么这样设计 | MySQL 设计规范、字符集和排序规则 | ER 图、数据字典、索引清单和迁移风险 |
| L3 事务与运行 | 慢查询、连接打满、主从或磁盘异常怎样定位 | 常见报错、主从、监控指标 | 指标截图或记录、排查步骤、修复前后验证 |
| L4 多模存储 | 关系、文档、搜索、消息、分析分别放在哪里 | MongoDB、ES、Kafka、Doris | 读写链路图、选型表、同步与失败策略 |
| L5 数据操作安全 | 导入导出、更新删除和配置变更如何控制范围 | 导出数据、Nginx、安装与运维资料 | 检查语句、变更语句、验证语句和回滚说明 |
| L6 数据产品意识 | 指标、口径、版本和权限如何影响结论 | SQL 场景题、监控与组件资料组合 | 指标口径卡、质量规则、权限与脱敏说明 |

对 AI/大数据岗位而言，L1 和 L2 不能用“会 SQL”概括；必须能说明粒度、重复、时间、空值和数据版本。对后端平台岗位，L3 至 L5 的操作安全同样重要。

## 可实操项目与交付物

### 项目一：事件数据到分析看板的最小链路

项目目标是展示事务数据、分析口径和查询性能之间的关系。使用自建或合成事件数据，禁止使用真实用户、医疗或生产库导出。

- 选择用户行为、订单状态或设备事件中的一种场景，先定义事件唯一标识、用户/实体标识、事件时间、写入时间和事件类型。
- 为事务侧设计 MySQL 表，按目录中的设计规范写清主键、字段类型、字符集和索引理由。
- 为分析侧设计 Doris 表时，明确表模型选择、查询维度、时间粒度和导入方式；资料没有覆盖的同步链路必须标为待补充。
- 写至少五条分析 SQL，例如日活、事件转化、TopN、连续行为、按维度累计；每条 SQL 都标注统计口径。
- 对一对多关联、重复事件、迟到事件、空值、跨天边界和时区分别设计测试数据。

建议交付物：

- 数据字典、ER 图、分析表字段表和指标口径卡。
- MySQL 与 Doris 的建表/查询脚本，脚本中不含真实连接信息。
- 样例数据、预期结果、异常数据和核对 SQL。
- 性能记录只填写实际测量的行数、耗时和环境；没有压测就明确写“未做容量验证”。

### 项目二：可追溯的检索与索引同步设计

项目目标是证明你理解数据库和搜索索引不是同一份真相。

- 设计一个知识条目或商品条目：关系库/文档库保存主数据，Elasticsearch 负责检索字段。
- 列出字段分工：哪些字段必须强一致读主库，哪些字段可接受索引延迟，哪些字段受权限控制不能进入索引。
- 设计新增、更新、删除三类同步事件，并分别说明失败、重复、乱序和重放时如何识别与补偿。
- 为搜索结果准备回查或版本校验规则，避免把旧索引结果直接当成当前业务真相。
- 把索引查询、同步日志和失败记录设计成可定位的证据链。

建议交付物：

- 主数据—事件—索引的时序图。
- 字段白名单、权限过滤规则和脱敏规则。
- 至少八个同步异常测试场景，包括重复、乱序、删除、部分失败和重建。
- 一份“为什么不直接把所有字段写进搜索索引”的解释。

### 项目三：Kafka 驱动的异步事件审计练习

项目目标是使用目录中的 Kafka 命令行资料，建立异步链路的最小正确性意识。

- 定义一个事件格式，包含事件 ID、事件类型、发生时间、实体标识、版本和载荷摘要。
- 用生产/消费命令验证事件能被传递；不把“收到消息”误写成“业务已经完成”。
- 明确至少一次消费带来的重复风险，并为消费侧定义幂等键或去重依据。
- 设计消费失败、重试、死信或人工处理的待补事项；当前资料未形成完整框架样例时应诚实标注。
- 把事件发送、消费处理、业务状态和审计查询分开描述。

建议交付物：

- Topic 和消息协议说明、生产消费验证记录、重复消息样例。
- 消费幂等设计说明和至少一条失败恢复流程。
- 一份不包含真实账号、地址和业务数据的本地运行手册。

### 项目四：数据库故障排查演练

项目目标是把监控资料变成排查能力，而不是背指标名称。

- 按目录中的连接数、QPS/TPS、慢查询、InnoDB 状态和磁盘空间维度构造四类故障现象。
- 对每类现象写“先观察什么—如何缩小范围—哪些操作不能贸然做—如何验证恢复”。
- 对慢查询记录 SQL、执行条件、索引假设和数据量；没有真实执行计划时不虚构优化结论。
- 对更新或删除操作始终先写检查查询，再写最小范围变更，最后写验证查询。

## 数据方案回答框架

面对任何存储或中间件选型题，可按以下顺序回答，而不是先抛组件名。

1. 先说明数据对象、写入频率、查询方式、时间边界、并发规模和正确性要求。
2. 再说明主数据、分析数据、搜索索引和消息事件各自的事实来源与可接受延迟。
3. 明确唯一键、幂等依据、重复/乱序/删除的处理，以及数据修复时的目标范围。
4. 给出监控信号：查询耗时、连接、积压、失败、磁盘、数据量或对账差异分别看什么。
5. 最后说明验证和回退：先用检查查询确认，再做最小变更，完成后用结果和指标复核。

## 简历与面试表达

### 简历写法

- 为事件或业务数据设计 MySQL 事务表与 Doris 分析表，沉淀字段字典、统计口径和 SQL 验证样例。
- 基于窗口函数、JOIN 和聚合完成若干业务场景 SQL，并针对重复、空值和时间边界保留测试数据。
- 设计主数据到搜索索引的同步链路，明确字段白名单、版本校验、重复/乱序和失败补偿边界。
- 建立数据库故障排查清单，覆盖连接、慢查询、InnoDB 状态和磁盘空间；只写真实演练或真实问题。

避免写“精通 MySQL/Kafka/ES”。用“完成什么数据模型、怎么验证、什么条件仍未覆盖”替代模糊级别词。

### 面试考察点

1. 一条指标 SQL 的统计粒度怎么确定？一对多 JOIN 为什么会让金额或人数被重复计算？
2. ROW_NUMBER、RANK、DENSE_RANK 等窗口函数在去重、TopN 和连续行为题中如何选择？
3. 设计一张高频写入的事件表时，主键、索引、时间字段、字符集和归档策略怎样权衡？
4. 慢查询、连接数打满、磁盘空间不足时，第一步分别看什么？为什么不能立刻重启或加索引？
5. Kafka 消费为什么会重复？幂等键、业务唯一键和偏移量各解决什么问题？
6. Elasticsearch 索引和主库数据不一致时，查询结果该如何处理？重建索引前要确认什么？
7. Doris 适合什么分析模式？和事务数据库相比，表模型和数据导入需要哪些额外考虑？
8. 数据修复 SQL 如何保证只影响目标记录？检查、变更、验证三类语句分别要写什么？
9. Nginx 在数据服务链路中承担什么职责？它不能替代哪些数据库或应用层问题？

## AI 协作方法

AI 可以帮助生成 SQL 初稿、测试数据和排查假设，但最容易在数据粒度、JOIN 基数和版本边界上“看起来正确却实际错误”。

1. 先提供脱敏 schema、主键/唯一键、字段含义、数据规模和指标口径，禁止直接上传生产库导出。
2. 要求 AI 在给 SQL 前先复述粒度、关联关系、时间范围和空值规则；复述错误就不要继续生成查询。
3. 让 AI 同时给出反例数据，尤其是一对多 JOIN、重复事件、迟到数据、空值、跨天和删除场景。
4. 让 AI 协助解释查询计划或索引候选，但最终以实际执行计划、监控和结果校验为准。
5. 在 Kafka/ES/Doris 设计中要求 AI 明确一致性假设、幂等键、失败恢复和重放策略，不能只输出组件名。
6. 对所有 AI 生成的更新、删除、DDL 和运维命令，先在最小样例验证，再由人工逐项确认目标范围。

## 当前资料缺口与补齐顺序

| 优先级 | 缺口 | 为什么必须补 | 建议补齐产出 |
| --- | --- | --- | --- |
| P0 | EXPLAIN、索引失效、事务隔离、锁和执行计划 | SQL 正确不等于可在生产稳定运行 | 慢查询复现、执行计划对比和索引取舍案例 |
| P0 | 数据仓库建模、指标口径、分区、数据质量与血缘 | AI/大数据岗位会追问数据从哪里来、是否可信 | 事实/维度模型、指标卡、质量规则与血缘图 |
| P0 | Kafka 消费组、分区、顺序、重试、幂等和可观测性 | 当前资料偏命令操作，无法支撑可靠事件链路 | 一套本地生产消费与故障恢复演练 |
| P1 | ES mapping、查询调优、索引生命周期和重建策略 | 检索系统需要长期维护而非一次写入 | 索引设计、同步对账和重建手册 |
| P1 | MySQL 备份恢复、权限、审计、迁移和容量规划 | 数据操作风险高，平台岗位会看恢复能力 | 演练记录、回滚方案和恢复验证 |
| P2 | CDC、实时同步、湖仓、调度与治理 | 连接 OLTP、流计算和数仓的关键能力 | 小型端到端数据链路和版本化文档 |

补齐先后顺序是：先把 SQL/模型/事务做对，再把消息和多模存储做可靠，最后扩展到实时同步和治理。每个新增案例都应含数据样例、验证 SQL、失败场景和安全边界。
