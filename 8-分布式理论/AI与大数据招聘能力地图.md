# 分布式理论：AI 与大数据招聘能力地图

分布式理论是 AI 平台、数据平台和高并发后端岗位的共同底座。它的价值不在于把 CAP、Paxos、Raft、TCC 名词背全，而在于面对网络分区、超时、重复、乱序、局部失败和节点故障时，能清楚地说明业务允许什么、系统保证什么、失败后如何恢复。

> 面试回答里最有说服力的不是“用了某个分布式组件”，而是能给出状态机、幂等键、时序、失败路径、对账与监控证据。

## 一、岗位关联：为什么 AI 与大数据也需要分布式理论

| 目标岗位 | 典型问题 | 本目录能力如何发挥作用 |
| --- | --- | --- |
| 大数据开发 / 数据平台 | 任务重复调度、数据重复写入、批次乱序、补数冲突 | 用幂等、唯一标识、状态机、事务边界和对账保证数据结果可解释 |
| AI 平台 / MLOps | 训练任务调度、模型版本发布、特征写入、推理请求重试 | 明确版本一致性、任务租约、缓存/锁、异步事件和回滚边界 |
| 后端 / 分布式系统 | 下单、库存、支付、消息和缓存一致性 | 选择强一致、最终一致、补偿、锁和 ID 方案，并评估代价 |
| 流计算 / 实时数仓 | 同一事件多次到达、迟到、重放、下游不可用 | 设计去重键、检查点、幂等 sink、重试和数据对账 |
| SRE / 平台工程 | 某节点、网络、存储或协调服务异常 | 根据故障模型确定降级、选主、隔离、恢复和观测策略 |

## 二、先建立正确的故障模型

单机程序里的“函数调用失败”在分布式系统中至少会分裂为多种情况：请求根本未到、请求到了但响应丢失、执行成功但调用方超时、执行多次、消息乱序、节点重启、时钟漂移或网络分区。设计前应先写清：

```text
调用方 ──请求──> 服务 / 任务
  │                  │
  ├─ 超时后是否重试？ ├─ 已执行但响应是否可能丢失？
  ├─ 怎样识别重复？   ├─ 状态如何持久化？
  └─ 下游不可用？     └─ 怎样补偿 / 对账 / 人工介入？
```

这张图决定了后续是否需要幂等、事务、锁、消息、补偿或人工核对。任何“只在正常路径成功”的设计都不足以应对数据任务和 AI 服务的真实运行环境。

## 三、核心概念如何转化为工程判断

### 1. CAP 与一致性：先说边界，再选方案

CAP 讨论的是发生网络分区时一致性（C）和可用性（A）的取舍，分区容错（P）在跨节点系统中通常无法回避。它不是“平时只能三选二”的口号，也不能直接替代业务设计。

| 业务对象 | 不能轻易错的内容 | 可接受的降级方式 | 需要证明的内容 |
| --- | --- | --- | --- |
| 订单/库存等关键状态 | 状态机、扣减结果、重复提交 | 拒绝/稍后重试、人工处理 | 幂等键、版本/条件更新、对账 |
| 数据指标/报表 | 最终统计口径和批次完整性 | 延迟产出、标记数据延迟 | 分区/批次范围、重跑和核对 |
| 模型/特征版本 | 模型与输入特征的兼容关系 | 暂停发布、回退旧版本 | 版本映射、灰度和回滚记录 |
| 推荐/分析类非关键结果 | 新鲜度或局部可用性 | 返回缓存、旧结果或空结果说明 | TTL、降级标识、恢复后校准 |

请先阅读 [CAP 理论](CAP理论.md)，再用自己的业务状态区分“必须立即一致”和“可最终收敛”的字段。

### 2. 共识与协调：理解，不滥用

[Paxos 算法](Paxos算法.md) 和 [Raft 算法](Raft算法.md) 的学习目标是理解多数派、任期、日志复制、选主和故障恢复的前提。工程上多数业务不需要自己实现共识协议；更重要的是知道协调组件/数据库为何会在节点或网络异常时影响可用性，以及为什么少数节点故障后不能无条件继续写入。

面试中可说明：共识解决的是“多个节点对同一顺序或状态达成一致”的问题，不等于所有跨服务业务都可以自然获得事务一致性。

### 3. 幂等、去重与全局标识

大数据与 AI 链路最常见的隐藏缺陷是“超时后重试造成重复结果”。应优先设计业务幂等：

1. 选择稳定的业务键或请求/批次 ID，而不是仅依赖随机重试次数。
2. 在存储侧用唯一约束、条件更新、版本号或去重表形成最终防线。
3. 将处理状态设计为可重入状态机，避免同一事件二次扣减、二次写入或二次触发任务。
4. 记录可对账的输入范围、输出范围和处理版本，以便重跑或补偿。

[分布式 ID 生成方案](分布式ID生成方案.md) 有助于比较 UUID、号段、雪花算法的唯一性、排序、吞吐和时钟依赖。但 ID 只是标识，不会自动实现幂等；二者必须一起设计。

### 4. 分布式锁：先问是否真的需要互斥

锁适合控制同一资源的并发临界区，例如同一任务只允许一个执行者、同一批次只允许一个调度者。它不适合作为所有一致性问题的万能解。

| 设计项 | 必须说明的问题 |
| --- | --- |
| 锁粒度 | 锁的是用户、订单、设备、批次、模型版本还是全局任务？过粗会串行，过细会失去保护。 |
| 所有者 | 如何证明“释放锁的人”仍是原持有者，避免误删他人的锁？ |
| 期限 | 执行时间超过 TTL 怎么办？续期、租约和任务中断分别如何处理？ |
| 失败行为 | 获取失败是等待、跳过、排队、重试还是人工处理？ |
| 可观测性 | 锁等待、获取失败、持有时长、过期和重复任务怎样监控？ |

结合 [分布式锁解决方案](分布式锁解决方案.md) 学习 Redis、ZooKeeper 等方案的前提与风险。先尝试唯一约束、条件更新、队列串行化或幂等设计，确有互斥需求再引入锁。

### 5. 跨服务一致性：事务、事件、补偿与对账

| 方式 | 更适合的前提 | 主要代价 / 风险 |
| --- | --- | --- |
| 本地事务 + 幂等事件 | 业务可拆分、允许异步收敛 | 需要可靠投递、重试、消费幂等和对账 |
| 2PC / 强协调 | 确实需要同步原子结果、参与方可控 | 可用性和复杂度成本高，故障恢复困难 |
| TCC | 操作可明确拆成 Try/Confirm/Cancel | 接口侵入大，需要处理悬挂、空回滚和幂等 |
| SAGA / 补偿 | 步骤可逆、可接受最终一致 | 补偿并非真正回滚，需面对外部副作用和人工边界 |
| 定期对账修复 | 允许事后发现并补齐 | 需要明确数据来源、口径、修复权限和审计 |

不要只报出模式名字；应从业务不可逆性、允许延迟、失败概率、依赖可控性、人工介入成本来说明选择。详见 [分布式事务解决方案](分布式事务解决方案.md)。

## 四、两个可实操作品 / 交付物

### 作品 A：可重跑的数据批次状态机

以“每日设备数据聚合”或“离线特征生成”为例，使用合成数据设计 `待处理 → 执行中 → 成功 / 失败 / 待补偿` 状态。交付内容应包含：

- 批次唯一键、输入时间范围、输出版本和处理人/任务记录。
- 超时、重复提交、部分写入、下游失败时的状态转移表。
- 幂等策略：唯一约束/条件写入/事务边界，以及安全重跑流程。
- 对账 SQL 或核对脚本：输入条数、输出条数、重复数、空值和时间范围。
- 失败演练说明：怎样重试、怎样隔离错误批次、何时需要人工确认。

### 作品 B：模型/配置灰度发布的版本契约

选择一个虚拟推理接口，定义模型版本、输入 schema 版本、特征版本、配置版本和发布批次的对应关系。提供一张时序图：新版本预检查、少量流量验证、观测延迟/错误/结果分布、扩大流量、异常回退。该作品重点不在实现复杂模型，而在证明你知道“进程启动成功”并不代表版本契约正确。

## 五、高频面试题与考察点

| 问题 | 建议回答要点 |
| --- | --- |
| CAP 是什么，如何用于实际选型？ | 说明网络分区前提；从业务对象出发区分强一致与最终一致，不将 CAP 当成所有架构决策的结论。 |
| 请求超时后是否应该重试？ | 先判断是否可能已成功；使用稳定请求 ID 和幂等设计；对不可安全重试的操作选择查询状态或人工边界。 |
| 分布式锁为什么会出问题？ | 锁过期、误释放、网络分区、进程暂停、续期失败、锁粒度过大和缺少监控都会导致错误；锁不能取代业务幂等。 |
| 什么时候选 TCC/SAGA，什么时候不用？ | 看可逆性、同步原子要求、参与方能力、失败处理和成本；可用异步事件+对账时不要为简单流程强上复杂事务。 |
| 雪花 ID 有什么风险？ | 机器/数据中心标识冲突、时钟回拨、顺序与分库分表热点、容量和运维配置；需要明确检测和容错。 |
| 如何保证数据任务重复执行不产生重复结果？ | 批次/业务键、存储唯一性或条件写、幂等 sink、状态机、输入输出范围记录和对账。 |
| Raft/Paxos 与业务分布式事务有什么关系？ | 共识解决副本一致的顺序/状态问题；业务事务仍要定义业务状态、外部副作用、补偿、幂等和审计。 |

## 六、面试与简历的证据表达

推荐使用“故障假设—设计—验证—边界”的写法：

> 为可重复执行的数据处理流程设计批次状态与幂等键，明确重复提交、超时、部分失败和补数的处理路径；以唯一约束/条件更新保护写入，并提供输入输出对账与失败重跑说明。实际项目中使用的组件、数据规模和结果只能填写自己能够证明的事实。

自查清单：

- [ ] 能用状态机和时序图讲清一个异步或跨服务流程。
- [ ] 能区分唯一 ID、业务幂等、锁和事务各自解决的问题。
- [ ] 能说出一次失败重试后如何避免重复副作用。
- [ ] 有一份对账/补偿/人工处理的边界说明，而不仅是正常流程图。
- [ ] 能为锁、事务、队列或批次处理定义至少一个可观测指标。
