# 近期项目实践与 AI 协作复盘

> 这不是“AI 自动完成项目”的成果清单，而是把最近真实工作中 AI 的作用、人工决策点和验证边界沉淀下来。适合与 [AI 工具在研发中的实践总结](AI工具在研发中的实践总结.md) 配合阅读。

## 一、最近工作的项目地图

| 项目 | 近期工作主题 | AI 更适合承担的部分 | 人工必须负责的部分 |
| --- | --- | --- | --- |
| `glucose-wave` | 血糖波动产品的前端与后端协作 | 页面骨架、组件、样式、交互状态和接口联调准备 | 数据模型、健康业务规则、接口、安全、验收 |

| `sino-scrm-backstage` | 活动试戴设备、轮次、奖励状态与统计 | 还原事件链路、生成只读检查 SQL、枚举早退条件 | 活动配置、真实日志/数据、生产修复授权 |

## 二、先统一：AI 的产出不等于已上线结果

最近项目中最重要的协作原则是把验证状态写清楚：

| 验证层级 | 可以说明什么 | 不能替代什么 |
| --- | --- | --- |
| 代码检索与差异检查 | 已定位真实文件、调用链或局部修改范围 | 不能证明接口在运行环境可用 |
| 编译与包级测试 | 受影响代码可编译，定向逻辑通过 | 不能证明数据库、缓存、消息或远端服务真实可用 |
| 匿名样例/文件核验 | 输入格式、字段、形状、文件副本或哈希满足预期 | 不能证明真实业务结果和模型效果正确 |
| 真实日志、数据库和接口验证 | 指定环境、指定数据样本下的实际行为 | 不能自动推广到其他活动、版本、配置或用户 |

因此，AI 的最终交付应始终包含三句话：**改了什么、验证了什么、还有什么限制或风险**。

## 三、案例一：用药主记录到健康日志——先修写入边界，不改错读模型

### 问题

编辑用药日期后，健康日历接口中的用药日期仍然陈旧。表面上是“查询结果不对”，但实际需要先确认接口的读模型、源数据和写入时序。

### AI 与人工的协作方式

1. 让 AI 沿“HTTP 接口 → 健康日志集合 → 用药主记录 → 保存后的日志写入”追踪真实链路。
2. 人工确认健康日历读取统一的健康日志读模型，用药主数据则来自独立记录；不能因为展示异常就把查询改到测量数据集合。
3. 定位异步后置写入会让保存先返回，且新旧保存可能乱序的问题。
4. 将日志写入调整为同步执行，并用按用药记录 ID 过滤的原子 upsert 更新；可变业务字段进入 `$set`，首次初始化字段进入 `$setOnInsert`，避免编辑时覆盖已有消息关联。

### 可复用经验

- “保存后立即可查”是明确的一致性承诺，异步写入前必须确认调用方能否接受延迟。
- 先画出读模型、源数据和写入边界，再决定改查询还是改写入。
- 原子 upsert 可以消除应用层“先查再插”的竞态，但仍要核对历史重复数据和数据库唯一索引。

### 验证边界

受影响 Go 包和随机顺序的定向测试已通过；未连接真实 Mongo/Redis，也未完成真实 HTTP 回归。因此不能宣称线上历史重复已清理或接口已在生产验证。

## 四、案例二：用药计划——把 `null` 当作业务语义，并在删除边界解除关联

### 问题

用药计划详情中的餐时字段有值却返回 `null`；删除计划后，历史用药记录仍保留已删除计划的关联。

### AI 与人工的协作方式

- 用 AI 按“数据库字段 → DTO → List/Detail 组装 → API JSON”逐层审计，发现时间和餐时字段没有成对组装。
- 人工确认餐时字段是可空指针：数据库 `NULL` 必须保持为 JSON `null`，不能用零值掩盖业务缺失；有值时也不能在组装中丢失。
- 继续追踪当前计划的统计契约，避免在查询层增加临时兜底；在删除计划的写入边界解除历史记录的计划 ID 关联，再删除提醒数据。

### 可复用经验

- 字段“已入库但没展示”常常是 DTO 或最后一公里组装遗漏，AI 很适合进行字段路径审计。
- `null`、空字符串和零值可能具有不同业务含义，不能为了前端方便自行互换。
- 删除并不一定意味着删除历史；需要明确保留什么、解除什么关联、失败后能否重试。

### 验证边界

logic/API 包级验证通过；未执行真实 Detail 接口、Mongo 更新或删除后的页面回归。

## 五、案例三：活动试戴设备抵消——用状态机和证据链取代“看界面猜规则”

### 问题

某试戴设备激活后，正装设备池没有更新。需要判断这是否是缺陷，并给出正确的抵消用户统计口径。

### 已确认的真实链路

- 试戴类型进入试戴营销处理后会直接返回，不会继续走普通正装设备池的更新路径。
- 试戴记录和正装设备池是不同的数据表；两者不能默认同步更新。
- 只有同一用户、活动、轮次存在可抵消的正装设备时，试戴流程才会标记该正装设备被抵消。
- `offset_device_sn` 非空才是“实际发生试戴抵消”的证据；统计抵消用户时应按该字段非空并对用户 ID 去重。
- 活动参与用户则应从用户轮次记录中按用户 ID 去重统计，不能用设备行数替代用户数。

### AI 与人工的协作方式

让 AI 沿“事件监听器 → 试戴服务分支 → 两张表写入 → 指定设备日志”建立证据链，再生成只读检查 SQL 和早退条件清单。人工再核对活动配置、同一用户/活动/轮次关系和线上数据，最后判断是否需要修复。

### 可复用经验

- 激活成功不等于正装设备池必须更新；状态、表归属、轮次匹配和实际抵消记录都要单独验证。
- 不要根据字段名、前端文案或截图虚构金额、退货、优惠等业务公式。
- 生产排查先输出检查路径与只读 SQL，确认事实后才讨论最小修复方案。

### 验证边界

结论基于具体代码、指定日志样本与统计 SQL；不能推广为所有活动、所有设备或所有环境的通用结论，活动配置变化后需要重新核对。

### 同一类生产排查中的“待闭环”案例

下面几类问题没有被包装成“已解决”，但很适合体现 AI 如何帮助缩小排查范围：

| 场景 | AI 可以先完成的工作 | 当前必须保留的边界 |
| --- | --- | --- |
| 黑名单设备仍需展示同步，但不参与活动 | 区分“同步设备池信息”和“计算轮次/奖励”两条路径，复用无活动状态枚举 | 代码差异检查通过，但 Maven 验证未完成，不能宣称已上线修复 |
| 小时任务改变奖励状态 | 还原状态机和调度入口，列出需要核对的奖励行、更新 SQL 与前端文案 | 具体数据库行、完整调度 SQL 和 UI 映射未闭环，根因不能下结论 |
| K8s/Nacos 下的 Redis 超时 | 分离 JSON 解析异常和 Redis/Lettuce 超时，整理 Pod、dataId、namespace、group 和覆盖顺序的检查清单 | 未取得完整调用栈、Pod 生效属性和 Nacos 内容，不能把单条超时日志当作根因 |

**共同经验**：生产环境里的 AI 结论应当标注为“代码已确认”“日志/数据已确认”或“待线上验证”。工具能加快证据收集，但不能替代真实运行环境和变更授权。

## 六、案例四：CGMformer 批量交付——文件完整性与结果正确性是两件事

### 问题

需要整理十批三分类结果，并确认交付文件没有因手工编辑、版本混用或格式变化而失真。

### AI 与人工的协作方式

- AI 协助生成独立核验器，逐批比对用户集合、顺序、数量、页签值、文本类型和 Excel `@` 格式。
- 人工确认标签的业务含义、最终交付版本与原始文件保留策略。
- 对已确认的交付副本做 SHA-256 一致性校验；原文件和修正文件分开保存，避免覆盖有争议的源文件。

### 可复用经验

- 文件副本的哈希一致，只能证明“复制没有变”；不能证明分类标签或业务语义正确。
- 批量交付至少要核对：集合、顺序、数量、值、类型、格式和全局覆盖。
- 原始文件与规范化文件应并存，验证结果要能追溯到确切输入和输出版本。

### 验证边界

十份修正副本的哈希一致性和汇总人数已完成；部分原始 XLSX 与最终 JSON 曾发现不一致。全部规范化文件的全局语义核验仍需在交付关闭前完成。

## 七、案例五：CGMformer 模型工程——模型契约必须显式、版本化、可验证

### 问题

为四分类文件上传服务准备 CSV/XLSX 输入、远程开发流程和模型启动条件，同时避免把旧实验结果误说成新模型效果。

### AI 与人工的协作方式

- AI 协助补齐文件解析、模板过滤、Schema 校验、远程运行配置和静态契约检查。
- 人工锁定具体模型版本、特征顺序、固定阈值、词表、权重与生产启动条件。
- 用匿名样例验证输入序列和表格特征形状，用编译和配置检查验证工程结构；权重缺失时服务应失败关闭，而不是用随机参数假装可用。

### 可复用经验

- 序列长度、特征维度与顺序、词表、标签映射、阈值、checkpoint、依赖和 IDE 路径都属于模型运行契约。
- “数据已审计”“服务可解析文件”“模型已训练有效”“真实推理已上线”是四个不同结论，不能混用。
- 整理工程时不要顺手移动大数据、权重、缓存或把不同实验代际混为一个版本。

### 验证边界

静态文件解析、匿名样例和部分工程配置已验证；未完成 GPU/CUDA 训练、真实权重启动、线上推理或新三分类准确率验证。

## 八、把这些案例变成可复用工作流

```text
明确目标和数据边界
        ↓
让 AI 先检索真实入口、数据源、调用链和相近实现
        ↓
人工确认业务语义、接口契约、状态机和授权范围
        ↓
AI 协助生成最小改动、检查 SQL、边界用例和验证命令
        ↓
按编译、测试、文件核验、真实接口/数据分层报告结果
        ↓
把已证实的结论沉淀为项目指令、提示词或 Skill
```

## 九、可以直接复用的提示词

```text
请在 <项目/模块> 中处理 <现象或目标>。

先确认真实执行链路：入口、业务服务、数据源、异步/事件、下游消费者和当前配置。
不要仅根据函数名、页面现象或字段名推断业务含义。

已知约束：
- <必须保留的业务语义，例如 null、历史记录、同一轮次>
- <不能改动的公共契约或数据范围>

请按以下顺序输出：
1. 已确认的事实与仍待确认的信息；
2. 最小修改或只读排查方案；
3. 需要覆盖的边界用例；
4. 已执行验证与未执行验证，不能夸大结论。
```

## 十、结论

最近工作反复证明：AI 的价值不是替人拍板，而是加速“还原真实链路、穷举边界、准备验证、整理证据”。涉及健康数据、模型输出、生产活动和跨服务调用时，业务语义、数据安全、上线授权和最终验收仍必须由负责人承担。
