# AI 工具在研发中的实践总结

> 分享主题：从“会聊天”到“能交付”——AI 工具在研发工作中的实践

## 一、分享结论

我目前使用 AI 的定位不是“让它替我写一段代码”，而是让它承担一部分可控的研发协作工作：快速理解项目、提出并落地最小改动、执行必要验证、沉淀可复用经验。

真正决定效果的不是一句万能提示词，而是四件事：给足上下文、明确边界、让 AI 调用合适的工具、要求它用验证结果交付。

```text
需求 / 故障现象
        ↓
项目规则 + 代码上下文 + 明确验收标准
        ↓
AI 分析、检索、修改、验证
        ↓
可审查的代码 / SQL / 文档 / 结论
        ↓
把有效经验沉淀为提示词、Skill 和记忆
```

## 二、实践覆盖的项目类型

| 项目类型 | 已有实践 | AI 工具带来的侧重点 |
| --- | --- | --- |
| Python 与模型工程 | Python 环境、FastAPI 部署、Hugging Face、DeepSeek-R1、CGMformer | 模型和服务的部署、资源与超时、日志和依赖管理 |
| Go 健康微服务 | 饮食图片分析、处方拍照识别、用药计划保存 | 真实服务编排、Agent 接入、接口契约和业务规则兜底 |
| 血糖波动项目（`glucose-wave`） | AI 完成前端页面与交互，人工主导后端 | 快速形成可用原型，同时用接口契约和验收守住质量 |
| Java AI 任务后台 | 数字人、视频/音频合成等异步任务管理 | 分层开发、任务状态、数据权限、异常与安全规范 |
| 运营与生产支持 | 活动奖励、实物配送失败补偿 | 代码、日志、数据库之间的证据链，以及最小风险修复 |

## 三、我使用的 AI 能力组合

| 能力 | 作用 | 实际使用方式 |
| --- | --- | --- |
| Codex | 代码理解、修改、测试、文档生成 | 在真实仓库中检索实现，按现有模式完成最小改动 |
| 项目级指令 | 把团队规范变成 AI 的长期工作边界 | 明确技术栈、分层、命名、接口、日志、验证和禁止事项 |
| 提示词 | 说明本次任务的目标、范围和验收标准 | 用业务规则、接口契约、异常分支约束 AI 的输出 |
| Skill | 把重复流程封装成可复用的工作卡片 | 文档、图片、表格、浏览器、代码审查等按场景调用 |
| 记忆 | 保存已经验证过的项目经验 | 记录真实接口、超时原因、验证命令和容易踩坑的边界 |

关键理解：提示词解决“一次任务怎么做”，项目级指令解决“在这个仓库里始终怎样做”，Skill 解决“某类工作怎样标准化执行”，记忆解决“下次不要从零开始”。

## 四、真实项目实践

### 1. 饮食图片识别与营养分析：把模型能力接入已有业务链路

**目标**：用户只传入 `imageUrl`；系统先调用健康服务识别图片，再进行营养分析，最终同时返回真实识别结果和分析结论。

**AI 协作方式**：

- 先定位已有的 Controller、DTO、路由、健康服务接口和相近的 Agent 实现，而不是凭空设计新接口。
- 明确约束：识别结果必须来自健康服务，不能由大模型“猜”；跨项目调用必须复用已有 HTTP/Feign 契约。
- 将必须先执行的图片识别放在业务逻辑层，而不是仅依赖 Agent 的 Tool 调用顺序。
- 当后续分析超过允许时间时，已成功的识别结果仍然返回，分析字段留空，避免整条链路因非关键步骤失败。
- 补齐路由绑定和 Swagger 可见性检查，避免出现“代码有了、接口却用不到”的问题。

**沉淀的方法**：AI 适合参与复杂业务编排，但关键服务调用、数据真实性和降级策略必须由业务代码保证，不能只依赖提示词约束。

### 2. 处方拍照识别：用业务规则约束模型的不确定性

**目标**：处方识别可能产生多个用药计划，支持一键批量保存；相同服药周期和时间的药品应合并，不同时间的计划才拆分。

**AI 协作方式**：

- 将“是否合并”的规则从自然语言落实为可执行的计划标识：规范化后的 `schedule_times + weeks`。
- 复用原有单条保存逻辑，保证提醒、明细和时间同步等既有副作用不被绕开。
- 在后端再次合并，抵消视觉模型把同一计划过度拆分的风险。
- 根据项目运行条件选择测试或编译验证，并如实说明无法执行完整测试的环境限制。

**沉淀的方法**：模型输出是候选结果，不是最终业务事实。要用确定的后端规则、去重逻辑和原有事务链路兜底。

### 3. 生产配送补偿：先查清真实行为，再生成可执行方案

**目标**：排查活动实物奖励发货失败，避免重复发货，并提供可执行的检查、更新和验证方案。

**AI 协作方式**：

- 先检索真实代码路径、订单字段、日志和数据库状态，不把“同步物流”和“重新创建订单”混为一谈。
- 区分只同步已有订单的接口与真正创建中台订单的接口，避免误操作造成重复发货。
- 将“远程调用失败后仍可追溯和补偿”的要求落实为：出站调用前先持久化足够的收货和订单数据。
- 输出时严格拆分检查 SQL、修复 SQL、验证 SQL，并限定到明确的表、字段和订单范围。

**沉淀的方法**：在生产问题上，AI 的价值不是直接给答案，而是帮助快速建立证据链；没有确认真实行为前，不执行扩大范围的修复。

### 4. Java AI 异步任务后台：让 AI 产出符合既有工程约束

**场景**：数字人、视频文字合成、音频与静音视频合成等任务都属于异步、状态可追溯、且需要数据权限控制的后端能力。

**AI 协作方式**：

- 通过项目级规则固定 Spring Boot 分层、DTO/实体边界、统一异常、安全校验和日志规范。
- 明确任务状态、外部任务 ID、媒体文件地址、完成时间等字段语义，避免 AI 随意改动任务状态机。
- 要求它在 Service 层完成业务和事务处理，Controller 只负责 HTTP 入参、响应和权限入口。

**沉淀的方法**：不同语言、不同项目可以有不同实现，但“先遵守本项目的稳定模式，再完成局部需求”的方法是一致的。

### 5. 血糖波动项目（`glucose-wave`）：AI 生成前端，人工守住业务后端

**分工**：前端页面、组件、样式和大部分交互由 AI 协助完成；后端由人工主导，负责数据模型、业务规则、接口、安全和最终验收。

**为什么这种分工有效**：

- 前端中大量工作具有可描述、可视化、可快速预览的特点，AI 可以显著加快页面骨架、列表、图表、表单和交互状态的产出。
- 血糖波动涉及数据口径、时间范围、异常值、用户数据和健康解释，后端必须由熟悉业务的人定义接口、校验和权限边界。
- 人工先提供接口字段、枚举、页面状态和验收截图，再让 AI 分模块实现，比“直接生成整个前端”更稳定、更容易回退。

**实践经验**：

- 先定接口契约，再生成页面：请求参数、返回字段、空态、加载态、错误态和权限态必须明确。
- 拆分页面任务：先布局和组件，再接接口，再补边界状态，避免一次生成后难以定位问题。
- 每次只验收一个页面或组件：核对设计、交互、接口字段、移动端适配和异常反馈。
- 前端代码仍需人工审查：关注重复组件、状态管理、请求取消、错误处理、权限控制和依赖安全。
- 健康数据只展示已定义的业务结论；AI 生成的文案不能替代医学判断，也不能把推测写成事实。

**沉淀的方法**：AI 最适合先把“看得见的产品原型”快速做出来；人工应把时间集中在业务正确性、数据安全、接口稳定性和最终体验上。

## 五、提示词怎么写才真正有用

我常用的任务提示词不是很长，但会包含以下六个要素：

| 要素 | 要说明什么 | 示例 |
| --- | --- | --- |
| 目标 | 最终要交付什么 | 为饮食图片新增一个分析接口 |
| 事实 | 已知项目和业务信息 | 识别接口在另一个服务，入参只有 `imageUrl` |
| 边界 | 不允许做什么 | 不新增 RPC、不改公共路径、不做无关重构 |
| 规则 | 关键业务判断 | 相同服药时间和周期必须合并 |
| 验收 | 怎样算完成 | 路由、Swagger、编译验证均需检查 |
| 输出 | 需要怎样汇报 | 只说明改动、验证、风险；SQL 分检查/更新/验证 |

### 通用研发提示词模板

```text
你在 <仓库 / 服务> 中完成 <目标>。

已知事实：
- <已有接口、模块、数据结构或错误现象>

业务规则：
- <必须满足的判断和异常分支>

修改边界：
- 只修改 <范围>；不要 <禁止事项>。
- 优先复用 <现有实现 / 接口 / 组件>，先阅读相近代码再动手。

验收要求：
- 检查 <路由、接口契约、数据一致性、权限、日志等>。
- 执行与改动范围匹配的 <测试 / 编译 / 静态检查>；若受环境限制，明确说明。

最终仅输出：改了什么、验证了什么、还有什么限制或风险。
```

### 生产排查提示词模板

```text
请排查 <业务现象>，先确认真实代码和数据行为，再给出方案。

范围：只允许检查 / 修改 <表、订单、服务>。
必须区分：<两个容易混淆的业务动作>。
先输出：排查路径和只读检查语句。
确认原因后，再输出：最小更新方案、回滚思路和验证语句。
禁止：根据猜测直接更新数据；扩大到未指定的用户或订单范围。
```

## 六、Skill 如何沉淀为团队能力

Skill 可以理解为“带操作步骤和工具约束的专业工作说明书”。它适合固化高频、容易遗漏、且需要一定专业流程的工作，例如：

- 文档生成：规定章节结构、渲染检查和交付格式。
- 图片生成或编辑：规定参考素材、视觉风格和输出尺寸。
- 表格处理：规定数据校验、公式、格式和最终核对。
- 浏览器自动化：规定登录态使用、页面操作和截图留证。
- 项目代码任务：规定检索范围、修改顺序、验证命令和最终汇报。

一个有效 Skill 不应只写“帮我做好”，而应明确：何时触发、先读哪些上下文、允许使用哪些工具、完成后如何验证、遇到阻塞如何说明。这样不同同事使用时，输出质量才会更稳定。

## 七、项目级指令：让 AI 像新同事一样遵守团队规范

我为 Go 微服务和 Java 后端分别维护项目规则。规则不追求面面俱到，重点放在 AI 最容易犯错、但项目最在意的地方：

- 先读同模块的成熟实现，再修改代码；不凭空引入新架构。
- 修改接口时同时检查 Controller、业务接口与实现、DTO/VO、路由、实体、常量和跨服务契约。
- 复用当前项目的数据访问、日志、异常、缓存、消息和命名习惯。
- 默认最小改动，不顺手重构；保留中文业务语义和已有兼容性。
- 用项目实际能运行的测试、编译或静态检查验证，并诚实说明环境限制。
- 不要提取很多不需要复用的小函数，减少人工审阅的成本

这类规则的价值在于把“经验丰富的人脑检查项”前置给 AI，降低其产出看似正确、实际不符合项目约定的风险。

## 八、推荐的日常工作流

1. **先定任务边界**：说明目标、影响范围、禁止事项和验收标准。
2. **让 AI 先读后改**：要求先定位相似实现、已有契约和真实调用链。
3. **分小步实施**：一次只解决一个明确问题，随时检查差异，避免大范围改动。
4. **把关键判断落到代码**：提示词只辅助推理；权限、顺序、幂等、数据真实性、超时与降级必须在系统中保证。
5. **用证据交付**：要求列出改动文件、验证命令和实际结果；失败时说明原因和影响范围。
6. **复盘并沉淀**：把反复出现的规则、故障原因、接口位置和验证方式补入项目指令、Skill 或记忆。

## 九、日常生活中可直接提效的用法

日常使用 AI 的原则和研发类似：把它当作“准备初稿、整理信息、辅助决策”的助手，关键事实和最终决定仍由自己确认。

| 场景 | 可以交给 AI 的工作 | 更有效的提问方式 |
| --- | --- | --- |
| 信息整理 | 把会议记录、长文、聊天记录整理成待办、结论和负责人 | 给出原始内容，并指定“按优先级、截止时间、负责人输出” |
| 写作沟通 | 起草邮件、周报、汇报提纲、通知、感谢或拒绝话术 | 说明对象、目的、语气、字数和必须保留的信息 |
| 学习提升 | 讲解陌生概念、制定学习路径、出练习题、批改思路 | 先说明当前基础，再要求“用例子解释并给我练习” |
| 计划安排 | 旅行行程、家庭周计划、购物清单、预算表、活动方案 | 给出人数、预算、时间、偏好和不可接受的条件 |
| 消费比较 | 对比产品参数、提炼评价关注点、列出选择清单 | 要求列出信息来源、适用人群和还需自行核实的内容 |
| 个人数据 | 清理表格、分类账单、生成统计和图表 | 先脱敏，只提供完成任务所需字段 |
| 创意表达 | 生成海报文案、图片描述、短视频脚本、亲子故事 | 明确受众、风格、时长、素材和禁用内容 |

### 一个简单的日常提问公式

```text
帮我完成 <目标>。
背景是 <已有信息>。
请按 <格式 / 语气 / 时间 / 预算 / 优先级> 输出。
不要假设 <不能确定的信息>；不确定的地方请标记为“待确认”。
```

例如："帮我把下面的会议记录整理成今天能执行的待办，按紧急程度排序，标注负责人和截止时间；没有明确负责人或时间的项标记为待确认。"

## 十、使用边界与风险控制

- **不直接相信生成结果**：代码、SQL、接口契约和生产结论都要依据仓库、日志、数据库和测试核验。
- **不暴露敏感信息**：不要把生产账号、密钥、完整用户隐私数据或未经脱敏的日志直接交给模型。
- **不让 AI 越权执行**：生产更新、删除、发货、消息发送等动作必须先确认目标和授权。
- **不以“能编译”替代“已验证”**：编译、单测、集成测试、路由可达性和业务验收各自解决不同问题。
- **不把记忆当成当前事实**：服务地址、配置、接口和数据状态可能变化，关键结论要回到当前环境复核。

## 十一、可直接用于分享的结束语

AI 工具最现实的价值，不是代替研发人员做决定，而是把检索、理解、重复编码、验证准备和知识整理这些工作加速。研发人员仍然负责业务判断、技术边界、数据安全和最终验收。

当我们把项目规范、任务提示词、Skill 和验证流程组合起来，AI 才会从一个通用聊天工具，变成能融入团队工程流程的可靠协作者。

## 十二、建议的 15 分钟分享安排

| 时间 | 内容 | 重点 |
| --- | --- | --- |
| 0-2 分钟 | 开场与结论 | AI 是协作者，不是自动驾驶 |
| 2-7 分钟 | 四个真实案例 | 业务规则、真实调用链、前后端分工和证据链 |
| 7-11 分钟 | 提示词、项目指令、Skill | 如何把个人经验变成稳定流程 |
| 11-13 分钟 | 工作流和生活提效 | 先读后改、小步验证、复盘沉淀 |
| 13-15 分钟 | 风险与答疑 | 数据安全、人工验收、生产边界 |

## 十三、分享前可准备的演示

- 展示一条带有目标、边界和验收条件的任务提示词，与一句“帮我改一下”进行对比。
- 展示 AI 在仓库中先检索接口、DTO、路由和相近实现，再产生最小修改的过程。
- 展示一次验证结果：代码差异检查、编译或测试结果，以及环境限制说明。
- 展示将一次排查结论沉淀为项目规则或 Skill 后，下次任务能直接复用的效果。
- 展示 `glucose-wave` 前端从接口字段到页面状态的一个小模块，以及人工如何验收接口和边界状态。

演示时不要使用真实生产敏感数据；提前准备脱敏分支、示例日志或录屏，避免现场网络和环境不稳定影响分享。
