# 服务器、运维和测试

## 章节定位

本章节面向服务部署、服务器管理、监控告警、日志分析和接口测试，是后端系统从“能运行”到“能稳定运行”的基础。

## 内容结构

```text
Linux 服务器
  ├─ 常用命令、磁盘、网络、时间、systemd
  ├─ Jar 包部署、GitLab、MinIO、MongoDB 开机自启
  └─ 服务器代理、磁盘空间、数据写入失败排查

监控告警
  ├─ Prometheus
  ├─ Alertmanager
  ├─ Grafana
  ├─ node_exporter
  └─ 数据库和中间件监控

日志平台
  └─ EFK + Logstash

测试工具
  ├─ Postman
  └─ Fiddler
```

## 运维排查总流程

1. 看服务是否启动。
2. 看端口是否监听。
3. 看日志是否有异常。
4. 看 CPU、内存、磁盘、网络是否异常。
5. 看数据库、中间件、第三方接口是否正常。
6. 看最近是否发布、改配置、扩容、迁移或证书过期。

## 生产环境基本要求

- 服务由 systemd、Docker 或 Kubernetes 托管。
- 日志有固定目录和保留策略。
- 核心接口有健康检查。
- 关键指标有监控和告警。
- 发布前有备份，发布后有验证，失败后有回滚方案。

## 适用场景

- 新服务第一次部署到测试、预发或生产环境，需要把启动方式、配置、日志和回滚方式交接清楚。
- 接口变慢、服务不可用、磁盘告急或告警触发时，需要按固定顺序缩小故障范围。
- 数据库、中间件、应用和第三方接口需要形成统一的可观测性与值守体系。
- 前后端、移动端或第三方系统联调前，需要先独立确认请求、鉴权和响应协议。

## 知识地图

- **运行底座**：从 [Linux 服务器](1-linux服务器/README.md) 的进程、端口、磁盘、网络和日志开始，先保证服务有可检查的运行环境。
- **交付与守护**：Jar 包、systemd、Docker 或 Kubernetes 负责启动和守护；部署时同时明确配置来源、日志位置、健康检查和回滚入口。
- **监控与告警**：Prometheus、node_exporter、数据库 exporter、Grafana 和 Alertmanager 共同回答“哪里异常、影响多大、谁来处理”。
- **日志与排障**：EFK + Logstash 用于集中检索；应用日志、系统日志和发布记录要能相互关联。
- **接口验证**：[测试工具](2-测试/README.md) 中的 Postman、Fiddler 和 curl 用于验证协议、鉴权、参数边界与网络链路。

## 学习与实践路径

1. 先在 Linux 上完成一次“查看服务状态 → 查看端口 → 查看日志 → 查看资源”的完整排查。
2. 选择一个普通应用，写出启动、停止、重启、查看日志和回滚的操作清单，并由 systemd、Docker 或 Kubernetes 其中一种方式托管。
3. 为应用补齐基础监控：主机资源、进程或容器、核心接口成功率和延迟，以及数据库或中间件的关键指标。
4. 用 Postman 或 curl 覆盖正常请求、缺少参数、鉴权失效、越权访问和分页/时间边界；需要抓取端侧请求时再使用 Fiddler。
5. 主动模拟一次磁盘满、依赖不可用或错误配置，验证告警、日志、定位步骤和回滚方案是否真实可用。

## 常见产出

- 服务部署与回滚清单、systemd 单元文件或容器部署说明。
- 环境变量和配置项清单，以及不含敏感值的配置说明。
- 监控仪表盘、告警规则、告警分级和对应处理手册。
- 接口测试集合、环境变量模板和联调问题记录。
- 故障复盘：时间线、影响范围、证据、根因、修复与预防动作。

## 维护建议

- 每次发布、扩容、迁移、证书或配置变更后，都更新部署记录和验证结果，避免排障时依赖记忆。
- 监控项必须写清指标含义、阈值、负责人和处理入口；只报警但没有处置路径的规则要及时补全。
- 日志保留策略、磁盘容量和时间同步应定期检查，防止“日志不可用”成为排障的第二个故障。
- 测试环境、接口集合和生产配置要分离管理；Token、密码、证书和真实业务数据不得写入文档或示例。
