# 服务器、运维和测试：AI 与大数据招聘能力地图

这份地图面向 AI 平台、数据平台、SRE、MLOps、测试开发和后端平台类岗位。这里的重点不是背命令，而是能够把“服务为什么不稳定、数据为什么不可信、模型为什么不可用”拆成可观察、可复现、可恢复的问题，并留下可核验的证据。

> 本目录已有 Linux、部署、监控、日志和接口测试材料。招聘场景中，应该把它们组织为完整的运行保障能力，而不是把每个工具说成孤立技能。

## 一、岗位定位：这部分能力能解决什么问题

| 目标岗位 | 面试官关心的结果 | 本目录对应能力 | 面向 AI / 大数据的延伸 |
| --- | --- | --- | --- |
| 数据平台 / 大数据开发 | 作业和数据链路能稳定运行、异常可定位 | Linux、磁盘、网络、日志、监控 | 识别批任务积压、存储容量、数据落盘失败和上游依赖异常 |
| AI 平台 / MLOps | 模型服务可发布、可观测、可回滚 | 服务托管、健康检查、告警、接口验证 | 关注模型版本、推理延迟、错误率、冷启动、资源和输入分布 |
| SRE / 运维开发 | 故障有预警、有证据、有处置闭环 | Prometheus、Grafana、Alertmanager、EFK | 将应用、数据库、中间件、数据任务和模型服务放进一张运行视图 |
| 测试开发 / 平台测试 | 接口契约、异常分支、上线验证可重复 | Postman、Fiddler、curl、日志排查 | 校验数据 API、特征服务和推理接口的 schema、鉴权、幂等与边界 |
| 后端 / 数据服务开发 | 不只会写接口，也知道如何交付和托底 | systemd、Jar 部署、配置、回滚 | 将数据处理或 AI 服务的运行说明一并交付，减少“代码能跑、环境跑不起来” |

## 二、招聘能力主线

```text
业务 / 数据 / 模型请求
        │
        ├─ 接口与鉴权校验 ──> Postman、curl、抓包
        │
        ├─ 应用与任务运行 ──> systemd / 容器 / 进程、端口、日志
        │
        ├─ 依赖链路 ───────> 数据库、缓存、消息队列、对象存储、第三方服务
        │
        ├─ 可观测性 ───────> 指标、日志、告警、发布记录、故障时间线
        │
        └─ 恢复与复盘 ─────> 降级、回滚、补数 / 重跑、根因和预防动作
```

一段合格的招聘表述应当同时回答五个问题：

1. **对象是什么**：哪个服务、作业、接口、主机或依赖出现异常。
2. **影响是什么**：影响哪些用户、哪个时间窗口、哪些数据或模型版本。
3. **证据是什么**：指标、日志、发布记录、请求样本或任务状态分别说明什么。
4. **恢复怎么做**：限流、重试、切流、回滚、补数或人工处理的顺序是什么。
5. **如何避免重复发生**：监控、告警、测试、容量、文档和演练补了什么。

## 三、核心能力拆解

### 1. Linux 与运行底座

掌握的目标不是记住全部命令，而是能在十分钟内回答“进程是否活着、端口是否监听、资源是否耗尽、日志在哪里、最近是否变更”。可按下面顺序排查：

1. 查看服务/进程状态，确认实例数量和退出码。
2. 查看端口、DNS、网络连通性和依赖地址，区分应用未启动与链路不通。
3. 查看 CPU、内存、磁盘 inode、磁盘空间、文件句柄和时间同步。
4. 以请求 ID、用户标识（脱敏）或任务 ID 为线索检索应用日志和系统日志。
5. 核对最近发布、配置、证书、扩容、迁移和权限变更。

AI 与大数据工作负载尤其要关注磁盘、对象存储挂载、临时文件、模型文件或大结果集造成的容量压力；但排查时不能把真实数据、Token 或生产连接串写入工单和示例。

可从 [Linux 服务器](1-linux服务器/README.md) 的系统查看、磁盘、网络、时间和 Jar 部署材料开始实践。

### 2. 监控、告警与日志：从“看到异常”到“能行动”

建议用四类信号组织监控面板，而不是只堆主机 CPU：

| 信号 | 常用指标或证据 | AI / 大数据场景中的解释 | 告警后第一步 |
| --- | --- | --- | --- |
| 流量 | QPS、消息积压、任务输入量、数据到达量 | 输入突增可能带来推理排队、作业排队或成本上升 | 对比正常基线和最近发布/活动 |
| 错误 | 5xx、异常数、失败任务数、重试数、数据校验失败数 | 区分调用失败、模型加载失败、schema 变化、依赖不可用 | 通过错误码和日志归类，先缩小影响面 |
| 延迟 | p50/p95/p99、队列等待、批任务时长 | 推理超时、Shuffle、数据库慢查询或网络抖动都可能导致变慢 | 分解为排队、处理、下游调用三个阶段 |
| 饱和度 | CPU、内存、磁盘、连接池、线程池、GPU/显存（如适用） | 资源满不等于根因，但会放大链路故障 | 先确认资源对象、阈值和持续时间 |

Prometheus 负责采集和规则计算，Grafana 负责看趋势与关联，Alertmanager 负责通知和分级，EFK/Logstash 负责检索上下文。任何告警都应配套：指标含义、阈值理由、影响级别、负责人、排查入口和恢复判定。相关材料见 [安装 node_exporter](安装node_exporter.md)、[监控平台](独立部署Prometheus%20Alertmanager%20Granfan监控平台.md)、[数据库和中间件监控规则](数据库和中间件监控规则.md) 与 [EFK 日志分析](搭建EFK+logstash日志分析系统.md)。

### 3. 数据与模型服务的运行契约

对于数据处理和 AI 服务，除了“接口 200”，还要验证下列契约：

| 契约 | 应验证的内容 | 常见失败方式 |
| --- | --- | --- |
| 输入契约 | 字段、类型、必填项、时间范围、单位、版本 | 上游字段改名、时间单位混用、空值或重复数据 |
| 输出契约 | schema、状态码、空结果语义、分页/批次语义 | 成功响应但结果为空、字段语义改变、重复写入 |
| 幂等与重试 | 请求 ID、任务 ID、重复提交后的行为 | 网络超时后重复消费、补数导致重复产出 |
| 版本契约 | 应用版本、数据版本、模型版本、配置版本可追溯 | 模型/特征不匹配、灰度无法回退、结果难以复现 |
| 安全契约 | 鉴权、最小权限、脱敏、审计 | 调试日志泄露敏感字段、测试环境误连生产 |

使用 [Postman](2-测试/postman.md) 或 curl 建立可导入的接口集合：至少包含正常请求、缺参、错误类型、鉴权失效、重复请求、时间边界和大请求体。抓包只用于合法的联调和定位范围，避免采集敏感业务内容。

### 4. 发布、回滚与变更管理

面试中“会部署”应能落到可审核的交付物：启动方式、版本号、配置来源、依赖、健康检查、验证步骤、回滚入口和负责人。一个可用的发布清单至少包括：

1. 明确本次代码、镜像或模型/数据版本及变更范围。
2. 在发布前校验配置差异、依赖可用性、磁盘容量和备份/回退前提。
3. 发布后验证进程、端口、健康检查、关键接口、核心指标和错误日志。
4. 灰度或观察窗口内监控错误率、延迟、资源与数据质量信号。
5. 异常时按预先定义的顺序执行降级、切流或回滚，并保留事件时间线。

对于离线数据作业，回滚不一定是删数据；更常见的是停止下游消费、隔离错误批次、按幂等规则重跑、对账并记录修复范围。

## 四、可直接准备的两类实战作品

### 作品 A：数据 / 模型服务可观测性方案

选择一个模拟的“设备数据分析 API”或“批处理指标服务”，不使用真实敏感数据，完成以下材料：

- 一张链路图：客户端、API、数据源、处理任务、存储和告警的关系。
- 一份接口集合：正常、异常、重复、越权和时间边界请求。
- 一个指标面板：请求量、错误率、p95 延迟、任务成功率、输入/输出量和资源使用。
- 三条带 Runbook 的告警规则：例如错误率升高、任务连续失败、磁盘容量不足。
- 一份复盘：构造故障、影响范围、证据、根因、恢复动作和预防措施。

面试时可以展示“如何从告警定位到一条具体请求/批次”，而不是只展示监控截图。

### 作品 B：上线验证与故障演练手册

将任意一个本地服务托管为 systemd 或容器，演示发布前后检查和一个故障演练。推荐演练：错误环境变量、磁盘占满、依赖端口不可达或接口鉴权失效。文档中必须明确安全边界：不在生产环境做破坏性操作，不记录密码、密钥、真实用户数据。

## 五、高频面试题：回答要点而非背诵答案

| 问题 | 推荐回答结构 |
| --- | --- |
| 接口突然变慢，如何排查？ | 先确认影响范围和基线；分解网关/应用/依赖耗时；用指标和日志关联；根据证据处理资源、慢查询、下游超时或发布回归；最后补监控和压测/回归。 |
| CPU 很高是不是立即扩容？ | 不是。先确认是持续饱和还是瞬时波动、哪个进程/线程/任务占用、是否有错误重试或数据倾斜；扩容是缓解手段，根因仍需闭环。 |
| 怎样设计告警避免告警风暴？ | 关注服务影响而非单点噪声；设置持续时间和合理阈值；分级、聚合、抑制和路由；每条告警都给出可执行的 Runbook。 |
| 数据任务失败后怎么重跑？ | 先冻结下游影响；确认输入范围、输出幂等键、已写入范围和依赖状态；选择安全重跑/补数/隔离；用结果对账验证，再恢复消费。 |
| 模型接口返回成功但效果异常怎么处理？ | 业务成功码不足以证明正确；核对输入 schema、单位、特征/模型版本、结果分布、发布记录和样本回放；必要时回退受影响版本。 |
| 为什么日志不能代替指标？ | 日志用于解释单个事件与上下文，指标用于聚合趋势和告警；两者通过请求/任务标识关联，缺一不可。 |

## 六、简历与面试证据清单

不要写“熟悉 Prometheus / Linux”后没有证据。可按“场景—动作—结果—边界”组织项目描述：

> 为某数据服务梳理发布与故障处置流程，覆盖健康检查、核心接口验证、主机/应用/依赖监控和日志检索；演练依赖不可用与磁盘容量告警，沉淀告警 Runbook 和回滚检查项。结果应填写可复核的实际指标或验证记录，未测量的内容不要虚构数值。

提交或面试前自查：

- [ ] 能画出服务、数据、模型/作业、依赖和监控之间的链路。
- [ ] 能解释一个告警阈值、影响等级和恢复判定。
- [ ] 有接口集合、配置模板、日志查询或复盘等可展示附件。
- [ ] 能说明一次重试、回滚或补数如何避免二次数据问题。
- [ ] 演示材料使用合成/脱敏数据，未暴露账号、Token、主机地址和真实日志。

## 八、能力边界与下一步补强

本目录偏向服务运行、监控、日志和测试基础。面向 AI 与大数据岗位，建议继续结合容器化、分布式理论、Hadoop/Hive/Spark 与流计算目录完成“数据进入—加工—训练/推理—服务—观测”的闭环。GPU 调度、模型注册、特征平台、数据血缘和统一追踪属于可进一步补强的专题；在没有真实环境和证据前，应表述为学习计划或实验能力，而不是生产经验。
