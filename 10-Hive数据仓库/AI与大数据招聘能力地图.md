# Hive 数据仓库：AI 与大数据招聘能力地图

Hive 是把大规模原始数据变成可查询、可解释、可复用数据资产的重要一层。面向大数据开发、数仓开发、数据工程、算法数据工程和分析工程岗位，核心竞争力不是“会写几条 Hive SQL”，而是能从业务问题出发定义数据粒度、口径、分层、分区、质量和下游影响。

> 本目录覆盖 Hive 核心概念、安装、DDL、DML、分区/分桶与查询。招聘准备应在这些内容上补齐“数据建模、指标治理、数据质量和 AI 数据集版本”的闭环。

## 一、岗位定位与能力信号

| 目标岗位 | 招聘方关心的产出 | Hive 能力信号 | 与 AI 的连接 |
| --- | --- | --- | --- |
| 数仓开发 | 主题域数据、分层表、稳定指标和报表 | 粒度、分区、ETL SQL、数据字典、血缘意识 | 为训练、标签、特征和离线评估提供可信输入 |
| 大数据开发 | 可按时运行且可重跑的离线任务 | DDL/DML、分区裁剪、性能、补数和对账 | 生成样本、特征或数据集快照，保证版本可复现 |
| 数据工程 / Analytics Engineering | 数据契约、质量、口径和下游协作 | schema、空值/重复处理、质量检查、发布流程 | 将业务数据翻译成算法/分析可用的标准数据集 |
| AI 数据工程 | 标签、特征、样本划分和版本管理 | 时间边界、实体去重、快照、权限、审计 | 防止数据泄漏、标签穿越和训练/评估口径不一致 |
| 数据分析 / 产品技术 | 指标查询、维度拆解、数据解释 | 聚合、关联、窗口函数、指标口径 | 用业务指标观测模型服务、特征供给或数据延迟 |

## 二、从业务问题到数据产品的链路

```text
原始日志 / 业务库 / 设备事件
          │
          ├─ ODS：原始落地、来源和批次可追溯
          ├─ DWD：清洗、去重、统一字段/时间/主键
          ├─ DWS：按主题聚合、沉淀复用指标
          ├─ ADS：面向报表、接口或特定消费场景
          └─ AI 数据集：样本 / 标签 / 特征快照与版本元数据
```

ODS、DWD、DWS、ADS 是常见的数仓表达，具体层级应遵循团队现有规范。面试时最重要的是：每一层的**粒度、主键、时间口径、分区字段、更新方式、输入来源、质量规则和下游消费者**都能说清。

## 三、核心能力拆解

### 1. 先定义表的“粒度”和“契约”

在写 DDL 之前，应回答“这张表一行代表什么”。例如一行代表一次事件、一个用户一天、一台设备一小时、一个订单明细还是一个模型预测批次。粒度不清会导致重复聚合、错误 Join、指标膨胀和训练样本泄漏。

| 契约项 | 需要写清的内容 | 常见风险 |
| --- | --- | --- |
| 业务粒度 | 一行对应的实体与时间范围 | 事实表被重复 Join，统计翻倍 |
| 主键/去重键 | 事件 ID、业务 ID、组合键、版本 | 重跑或上游重传产生重复记录 |
| 时间口径 | 事件时间、入库时间、业务日期、时区 | 跨天、迟到数据和报表口径不一致 |
| schema | 字段名称、类型、单位、是否可空、含义 | 字段改名、类型漂移、单位误用 |
| 更新方式 | 全量、增量、拉链、覆盖、追加 | 历史值被覆盖、补数污染已发布数据 |
| 下游契约 | 报表、接口、任务、特征/标签的消费方式 | 改表后下游静默出错 |

[Hive 简介及核心概念](Hive简介及核心概念.md) 与 [Hive DDL 操作](Hive%20DDL操作.md) 可作为建立元数据、表和视图基础的起点。

### 2. 分区、分桶与文件组织

分区服务于数据裁剪和生命周期管理，常见字段是业务日期/小时；分桶更适合明确的采样、关联或分布需求，但不是“加上就一定快”。

| 设计选择 | 适合的判断 | 要验证的代价 |
| --- | --- | --- |
| 按天/小时分区 | 查询与补数常按业务时间过滤 | 分区数量、迟到数据、跨分区查询和保留策略 |
| 静态 / 动态分区写入 | 批次范围是否可预先确定 | 写入范围是否越界、动态分区数量和资源消耗 |
| 分桶 | Join、抽样、倾斜治理有明确需求 | 桶数、数据均匀性、写入/读取兼容性与维护成本 |
| 小文件治理 | 多次小批写入或上游文件碎片化 | NameNode/元数据、任务数量、扫描和合并成本 |
| 列式存储 / 压缩 | 读取列少、数据量大、分析查询为主 | 压缩比、CPU、兼容性和执行引擎支持 |

分区的本质是**数据边界**：生成、校验、补数、过期和权限都要与之对齐。参考 [Hive 分区表和分桶表](Hive分区表和分桶表.md)。

### 3. SQL：正确性、可读性和成本同等重要

Hive SQL 常被面试为 Join、窗口函数、去重、留存、漏斗和 TopN，但真实工作还应关注：

1. 在查询开始就限制分区和字段，避免无意全表扫描。
2. Join 前确认两侧粒度、唯一性和空值，避免多对多展开。
3. 用窗口函数前明确排序字段和并列值语义，避免不稳定排名。
4. 把重复的业务口径沉淀到视图/中间层或文档，避免复制粘贴后漂移。
5. 用样本、边界日期、重复记录、空值和异常值验证结果，而不是只看 SQL 能执行。

[Hive 数据查询详解](Hive数据查询详解.md) 是练习复杂查询和窗口函数的基础；[Hive DML 操作](Hive%20DML操作.md) 用于理解写入和数据变更边界。

### 4. 数据质量、补数与可重跑

数据质量不是任务成功状态。建议为每个正式分区定义最小校验集：

| 校验 | 示例 | 失败后处理 |
| --- | --- | --- |
| 完整性 | 分区是否到达、行数是否异常下降 | 暂停下游发布，核对上游批次和迟到数据 |
| 唯一性 | 业务键是否重复、重复比例是否异常 | 去重、隔离问题批次，确认重跑范围 |
| 合法性 | 枚举、数值范围、时间范围、单位 | 标记/隔离异常，向上游反馈契约问题 |
| 一致性 | 与源表/前一层行数、金额、实体数是否可对账 | 记录差异并定位过滤、Join、时区或批次问题 |
| 新鲜度 | 分区/任务是否按 SLA 产出 | 告警、补数、记录数据延迟状态 |

补数前先明确源数据范围、目标分区、下游依赖、是否覆盖、重跑幂等和验证口径。生产环境中禁止凭感觉执行宽泛的 `INSERT OVERWRITE` 或删除操作。

## 四、AI 数据工程的特别关注点

AI 训练、评估、特征和标签需要的不是“更多数据”，而是**同一版本、同一口径、可复现且无泄漏的数据**：

- 将原始事件、清洗结果、标签、特征和训练/评估快照分层，不让模型直接读取未治理的原始表。
- 对每个数据集快照记录 SQL/作业版本、源分区、过滤条件、schema、实体数、时间范围和质量结果。
- 按实体或时间划分训练/验证/测试集，避免同一实体跨集合或用未来事件构造过去特征。
- 明确特征时间点与标签观察窗口，防止标签穿越；这比模型参数更容易造成虚假的离线指标。
- 健康、设备、用户等敏感数据必须最小权限、脱敏和审计；练习和面试作品只用公开或合成数据。

## 五、两个可实操作品 / 交付物

### 作品 A：从原始事件到指标宽表的数仓小项目

用公开或合成的订单、日志或设备时序数据，设计 ODS、DWD、DWS、ADS 四层中的最小闭环：

- 绘制主题域和表关系，写清每张表的粒度、主键、分区、字段字典和来源。
- 提供 DDL、初始化/增量 DML、分区生成和一组查询 SQL。
- 给出至少三条质量检查：行数、新增/去重、字段范围或源表对账。
- 构造一次迟到数据/重复数据，说明如何补数、重跑并验证下游指标。
- 形成数据字典、血缘草图、SQL 版本和结果截图（使用合成数据）。

### 作品 B：面向模型训练的特征与标签快照设计

选择一个不含敏感数据的预测主题，使用 Hive SQL 产出特征表和标签表，并写明：实体/时间粒度、特征可用时间、标签窗口、训练/验证/测试划分、抽取分区、schema 版本、质量检查和回滚策略。重点是证明数据治理能力，不需要夸大为生产模型效果。

## 六、高频面试题与考察点

| 问题 | 建议回答要点 |
| --- | --- |
| 分区表为什么通常更快？ | 查询能进行分区裁剪、减少扫描；前提是过滤条件使用分区字段且分区数量/文件规模可控。 |
| 分区和分桶如何选择？ | 分区用于强时间/业务边界和裁剪，分桶用于明确的分布/Join/采样需求；说明维护代价和验证方式。 |
| Join 后数据翻倍怎么排查？ | 先检查两表粒度、主键唯一性、重复数据和 Join 条件；不要先靠 `distinct` 掩盖数据问题。 |
| 如何处理迟到数据和补数？ | 明确事件时间与业务日期、补数窗口、目标分区、覆盖/追加策略、下游影响和对账。 |
| 为什么小文件是问题？ | 元数据、调度、启动与扫描开销增加，降低查询/作业效率；需从写入批次、合并和文件组织治理。 |
| 怎样保证 AI 训练数据不泄漏？ | 固化时间点、数据快照和实体划分；特征仅使用预测时刻可获得的信息，标签/未来信息不能反向进入特征。 |
| 表结构变更要注意什么？ | 评估存量数据、兼容性、下游 SQL/报表/接口、schema 版本和回滚；通过文档和测试避免静默错误。 |
