# 区块链相关技术：AI 与大数据招聘能力地图

## 使用范围

本页围绕目录中的 Hyperledger Fabric、Fabric CA、Raft 排序服务、测试网络、Cello、FISCO BCOS 和 Java SDK 资料，整理联盟链后端、可信数据平台和企业集成岗位的招聘准备路径。

区块链并不是 AI 或大数据岗位的通用必需项。它更适合证明你能处理多组织身份、网络配置、不可篡改证据、合约调用和企业系统集成；不要把它包装成所有数据问题的默认方案。

## 岗位关联

### 联盟链与企业后端集成

- Hyperledger Fabric 路线覆盖测试网络、Peer、Orderer、Raft、Fabric CA、证书、通道、Chaincode 和 Cello 管理等内容，适合联盟链平台或企业系统接入岗位。
- FISCO BCOS 路线覆盖节点/控制台与 Java SDK，适合 Java 后端将账户、合约和链上查询接入业务系统的场景。
- 招聘中最重要的不是“启动过链”，而是能说明组织身份、证书、网络、合约、交易提交和查询验证如何串成一条可信链路。

### AI 与可信数据

- AI 相关场景可将链用于关键结果、数据版本、审核动作或跨组织凭证的可追溯证明，但不应把原始隐私数据、模型全部输入或大文件直接当作链上存储对象。
- 候选人需要区分“链上证明什么”和“业务系统保存什么”。目录现有资料能支持网络、账户、证书和 SDK 的基础说明，但隐私计算、模型治理和数据合规仍是资料缺口。
- 若岗位是普通 AI 应用后端，区块链能力应作为可信审计/多方协作加分项，而不是替代 API、数据库、数据治理和模型工程基础。

### 大数据与数据平台

- 联盟链可以承担跨主体的数据凭证或操作审计，但不替代数仓、检索、消息和分析引擎。
- 面试中可说明：链上存业务摘要、版本、哈希或审批事件；链下系统负责明细、查询、权限和分析。具体方案仍需验证数据合规和性能。
- 这样的边界意识比泛称“区块链保证数据安全”更可信。

## 可实操项目与交付物

### 项目一：Fabric 可信凭证登记与查询演练

项目目标是跑通“组织/证书 → 测试网络 → 交易提交 → 查询验证”的完整最小链路。业务内容可以是模拟凭证或版本摘要，不使用真实客户数据或私钥。

- 为凭证定义业务标识、版本、摘要、提交方组织、提交时间和状态；说明哪些内容上链，哪些只保留链下。
- 按 Fabric 测试网络资料完成环境准备，记录 Docker、网络、节点和通道的状态，不省略验证步骤。
- 用 Fabric CA/证书资料解释调用账户的身份来源；私钥、证书路径和连接配置只以占位符或脱敏形式记录。
- 提交一笔登记交易后，立即通过查询验证状态和字段，不将“命令返回成功”当作最终业务成功。
- 模拟重复登记、无权限身份、网络不可达、合约调用失败和查询不到数据等异常。
- 如当前资料没有完整 Chaincode 开发案例，应将合约实现明确列为补充项，不虚构已实现的合约能力。

建议交付物：

- 网络拓扑图、链上链下字段表、身份/证书关系图。
- 环境启动与验证手册、交易提交和查询证据。
- 异常清单、排查顺序和恢复/重试的限制说明。

### 项目二：FISCO BCOS Java SDK 业务接入样例

项目目标是证明后端服务如何以受控方式调用联盟链，而不是只在控制台操作。

- 基于 FISCO BCOS Java SDK 资料设计一个 Java 服务接口，输入为脱敏的业务摘要，输出为交易或查询结果。
- 将账户管理、合约客户端、业务参数校验和异常转换分开，避免控制器直接操作私钥或链连接。
- 明确配置项的来源：节点地址、账户配置、合约标识和超时类参数应可外部注入；真实密钥不能写进代码、日志或文档。
- 对连接失败、账户无权限、交易失败、交易已提交但查询尚未可见、合约地址错误分别定义接口返回和日志上下文。
- 用模拟或测试网络完成一次写入和一次查询；如果没有可信环境，不要伪造交易哈希或截图。

建议交付物：

- Java 调用分层图、配置项白名单、接口契约和异常对照表。
- 交易调用与查询验证记录，注明网络版本和测试环境。
- 一份安全审查清单，覆盖私钥、日志、异常信息、权限和配置权限。

### 项目三：证书与网络变更风险演练

项目目标是把“会部署”升级为“知道如何安全维护网络”。

- 根据 Fabric 部署教程中的 Raft、TLS 证书轮换、证书到期和指标内容，列出网络变更前的检查项。
- 为证书轮换设计测试环境步骤：当前证书、目标证书、受影响节点、重启/重配置顺序、验证方式和回退条件。
- 对节点不可用、TLS 失败、通道配置不一致和客户端连接异常，按网络层、证书层、通道层、SDK 层顺序排查。
- 只在隔离测试环境演练；不修改任何生产证书、通道或排序服务配置。

## 方案边界自检

- 是否能说清为什么此业务需要多组织可信记录，而不是普通数据库审计或签名即可解决。
- 是否已把原始明细、个人信息、模型输入与链上摘要、版本、哈希、审批事件分开。
- 是否明确每个组织、账户、证书和合约调用者的权限，而不是把管理员账户当作业务账户。
- 是否同时验证了交易提交、交易状态和业务查询，而不是只保留一次命令成功的截图。
- 是否为节点不可用、证书过期、网络不通、配置错误和合约失败准备了停止与排查顺序。
- 是否写清平台版本、测试环境、依赖软件和配置来源，避免 Fabric 与 FISCO BCOS 的材料混用。
- 是否把密钥、证书私密内容、真实节点和生产组织信息从文档、截图和日志中移除。

展示项目时优先按照“为什么上链 → 链上/链下边界 → 身份与网络 → 交易与查询验证 → 故障与安全限制”的顺序讲。先讲组件安装，通常无法说明真正的业务价值和风险控制。

任何演示都应只使用测试网络和合成业务摘要，并将证书与账户配置的展示范围控制到可公开字段。

最终交付建议附带：

- 网络和组织拓扑图。
- 身份与权限边界表。
- 交易提交与查询验证记录。
- 故障场景及停止/恢复条件。

这些材料应能让另一位工程师在同一测试环境中复核结论。

## 简历与面试表达

### 简历写法

- 在 Fabric 测试网络中完成联盟链凭证登记与查询演练，输出组织/证书关系、交易校验和异常排查手册。
- 基于 FISCO BCOS Java SDK 设计后端调用边界，区分账户配置、合约客户端、参数校验和错误转换，并使用测试网络验证。
- 完成证书与网络变更风险清单，覆盖 TLS、Raft、通道配置、节点状态和回退验证。
- 对 AI/数据场景定义链上摘要与链下明细边界，明确区块链不替代数仓、搜索或原始数据治理。

只写真实搭建、测试和验证范围。没有合约开发、性能压测、生产部署或安全审计证据时，应在项目说明中如实标出。

### 面试考察点

1. 联盟链与公链的业务、身份和权限边界有什么不同？什么情况下不应该引入区块链？
2. Fabric 中 Peer、Orderer、通道、组织、Chaincode 和 Fabric CA 分别承担什么职责？
3. 为什么“交易提交成功”还需要查询验证？交易结果、账本状态和业务状态有什么差别？
4. 证书过期、TLS 失败或证书路径错误时，如何区分网络问题、身份问题和 SDK 配置问题？
5. Raft 排序服务解决什么问题？它和业务数据一致性、合约执行边界如何关联？
6. Java 服务接入 FISCO BCOS 时，私钥、节点配置、合约地址、超时和异常信息应该怎样管理？
7. 数据或 AI 结果为什么不宜全部上链？链上摘要、版本、哈希和链下明细如何配合？
8. 多组织业务中，权限、审计、数据可见性和监管要求如何影响合约及链下系统设计？
9. 合约升级或网络配置变更前，为什么要准备兼容、验证和回退方案？

## AI 协作方法

AI 可以帮助解释拓扑、生成测试清单和梳理配置差异，但区块链命令、证书和网络配置有较高操作风险。

1. 只提供脱敏的拓扑、版本、错误摘要和配置键名，绝不粘贴私钥、证书私密材料、生产节点地址或管理员账号。
2. 让 AI 先按网络、组织、证书、通道、合约、SDK 六层输出排查树，再用当前环境状态逐层证实。
3. 对每个生成的命令要求标明目标环境、影响对象、是否可逆、预期现象和失败后的停止条件。
4. 让 AI 帮助设计链上/链下字段白名单、交易异常矩阵和证书轮换检查表，而不是直接生成生产脚本。
5. 所有网络初始化、证书轮换、删除用户或重配置操作都必须先在测试环境验证，并由人工确认实际路径与版本。
6. 对 AI 提供的合约或 SDK 样例进行版本、权限、异常、隐私和性能审查；不能因代码可编译就认为可上链生产。

## 当前资料缺口与补齐顺序

| 优先级 | 缺口 | 招聘影响 | 建议补齐产出 |
| --- | --- | --- | --- |
| P0 | Chaincode/合约开发、测试和生命周期 | 现有资料更偏网络与环境，无法证明业务合约交付 | 一个最小合约、单元/集成测试和升级说明 |
| P0 | Fabric/FISCO 的端到端 Java 服务样例 | SDK 文档不能单独证明企业集成能力 | 配置外置、调用、查询、异常和权限测试项目 |
| P0 | 私钥管理、访问控制、审计、隐私与数据合规 | 可信系统的安全边界是高频追问 | 威胁模型、字段分级、密钥与日志规范 |
| P1 | 性能、容量、并发、账本/状态数据库与监控 | 测试网络可用不等于生产可用 | 基准测试、指标、故障排查和容量记录 |
| P1 | 合约升级、数据迁移、证书轮换与灾备 | 企业网络长期维护必需 | 变更计划、回退方案和演练记录 |
| P2 | 与数据平台、AI 审计、跨组织治理的完整案例 | 有助于差异化，但需先有基础交付证据 | 链上摘要/链下明细的端到端设计与评审 |

补齐顺序是：先完成 P0 的合约和 Java 集成闭环，再补安全与运行证据，最后扩展到 AI/数据的可信审计场景。每个实践都应清晰写明平台版本、测试环境、密钥脱敏方式、验证步骤和风险边界。
