# Spark 大数据引擎：AI 与大数据招聘能力地图

Spark 是离线 ETL、交互式 SQL、批量特征处理和部分流式计算中常见的统一计算引擎。面向大数据开发、数据工程、数仓开发、AI 数据工程和平台工程岗位，真正需要证明的是：能把数据契约、执行模型、性能问题、任务可靠性和结果质量组织成一个可运行、可诊断、可复现的作业。

> 本目录已有 RDD、算子、Spark SQL 和 Spark Streaming 的基础材料。招聘准备时应从“会写 API”升级到“知道作业为什么慢、怎么避免重复结果、如何为 AI 数据链路提供稳定输入”。

## 一、岗位定位与能力信号

| 目标岗位 | 常见工作内容 | Spark 能力信号 | 与 AI 的连接 |
| --- | --- | --- | --- |
| 大数据开发 | 离线清洗、聚合、宽表、数据导出 | DataFrame/SQL、分区、Shuffle、作业提交、结果校验 | 生成训练样本、标签、特征、嵌入或批量预测输入 |
| 数据平台工程 | 作业资源、失败重试、数据链路稳定性 | Driver/Executor、资源参数、日志、队列、运行指标 | 保障大批数据准备、模型批推理和数据集快照准时产出 |
| AI 数据工程 | 训练数据构建、特征工程、数据质量 | schema、时间边界、去重、可重跑、数据版本 | 防止泄漏、漂移、重复和训练/评估数据不一致 |
| 数仓开发 | Hive/湖仓数据加工、指标与报表 | Spark SQL、Join、窗口、分区裁剪、文件组织 | 将离线指标和特征供给下游模型与业务服务 |
| 实时/流处理开发 | 微批处理、流式聚合、实时输出 | 输入/输出语义、批次、检查点、幂等 | 面向在线特征、事件流或监控数据，但需补齐现代流式语义 |

## 二、从一行代码到集群执行的模型

```text
提交应用
   │
   ├─ Driver：构建逻辑计划 / DAG，申请资源，协调任务
   │
   ├─ Executor：在节点上执行 Task，读写分区数据，缓存中间结果
   │
   ├─ Stage：被 Shuffle 边界切分的执行阶段
   │
   ├─ Partition：并行处理和数据分布的基本单元
   │
   └─ Input / Shuffle / Output：决定 I/O、网络、倾斜、文件与结果可靠性
```

面试时不要只说“Spark 内存计算很快”。更有价值的是解释一个具体作业的输入是什么、分区如何设置、哪里发生 Shuffle、为何缓存或不缓存、输出如何幂等、慢任务怎样定位。

## 三、核心能力拆解

### 1. RDD、DataFrame、Dataset 与 SQL：按问题选抽象

| 抽象 | 更适合的使用场景 | 需要理解的边界 |
| --- | --- | --- |
| RDD | 低层转换、理解血缘/分区/算子，或复杂非结构化处理 | 灵活但优化空间和类型/schema 管理更依赖开发者 |
| DataFrame | 结构化数据清洗、聚合、Join、ETL | 关注 schema、表达式、执行计划与列裁剪 |
| Dataset | JVM 生态中同时关注类型与结构化处理时 | 需要理解编码器、语言生态差异和执行计划，而非把它当作性能保证 |
| Spark SQL | 数仓/分析场景、复用 SQL 逻辑和降低协作门槛 | 仍需关注分区、Join、扫描范围和输出契约 |

[Spark 简介](Spark简介.md)、[Spark RDD](Spark%20RDD.md)、[Spark 算子详解](Spark算子详解.md) 和 [SparkSQL 简介](SparkSQL简介.md) 共同构成这条能力线。应至少用两种抽象实现同一数据转换，比较代码可读性、schema 和执行计划，而不是只比较是否运行成功。

### 2. 分区、Shuffle 与数据倾斜：性能面试的主线

| 现象 | 可能原因 | 应先收集的证据 | 可能方向 |
| --- | --- | --- | --- |
| 某些 Task 明显更慢 | 热 key、分区不均、文件大小差异、单节点资源异常 | Stage/Task 时长分布、输入大小、key 分布、Executor 日志 | 调整 key/预聚合/拆分热点、重分区或处理异常节点 |
| Shuffle 数据量很大 | 宽依赖、Join/聚合前数据未过滤、重复列 | 执行计划、过滤位置、Shuffle read/write、字段与行数 | 尽早过滤/裁剪，优化 Join/聚合逻辑，避免盲目调内存 |
| 小文件过多 | 上游频繁小批写入、不合理分区/输出 | 文件数量、平均大小、任务数量、NameNode/扫描开销 | 合并文件、改善写入批次和输出分区 |
| Executor OOM / 频繁 GC | 单分区过大、缓存滥用、广播过大、内存参数不匹配 | GC、峰值内存、失败栈、分区大小、缓存使用 | 先修数据分布/缓存策略，再基于证据调资源 |
| 输出文件过多或重复 | 输出分区未控制、重跑缺少批次边界 | 输出目录、文件清单、批次 ID、下游读取逻辑 | 明确临时输出/成功发布、控制分区和幂等写入 |

性能优化应该是“基线 → 证据 → 单一改动 → 复测 → 回退方案”的闭环。仅仅增加 Executor 数或内存可能掩盖问题，甚至放大资源抢占。

### 3. Join、聚合和窗口函数：先验证数据，再谈优化

面对两表关联，应按以下顺序思考：

1. 两边各自的行粒度和唯一键是什么？是否会产生多对多展开？
2. 是否可以先按日期/条件过滤并选择必要列，减少扫描和 Shuffle？
3. 小表是否足够小且稳定，能否考虑广播；广播失败或过大怎么办？
4. key 是否存在热点，空值和异常 key 如何处理？
5. 输出是否按业务键和批次幂等，重跑如何避免重复？

相同原则也适用于 AI 特征拼接：先固化实体键和特征可用时间，再做 Join；不能用未来数据“填充”过去样本。

### 4. 缓存、血缘和失败恢复

缓存只适合会被多次复用、计算昂贵且资源可承受的中间结果；缓存不是默认写法。应能说明缓存级别、驱逐影响、`unpersist` 时机和当缓存失效时血缘重算的代价。

Spark 的血缘和失败重算帮助理解容错，但不会自动解决外部副作用：向数据库、消息系统或文件目录写结果时，仍需设计批次 ID、临时目录、成功标记、幂等 sink 和结果对账。

### 5. Streaming：理解当前材料的范围

[Spark Streaming](Spark%20Streaming.md) 介绍的是微批处理基础。准备实时岗位时，除了 DStream/微批模型，还应补强 Structured Streaming、watermark、迟到数据、状态存储、checkpoint、输出幂等与端到端语义。当前目录未覆盖这些专题，不应据此夸大为生产级实时计算经验。

## 四、AI 数据工程的特别关注点

Spark 适合大规模构建训练/评估数据集、特征快照和批量预测输入，但必须把“正确性”放在“吞吐”之前：

- 每次作业记录输入分区、schema、代码/配置版本、过滤条件、输出路径与数据质量结果。
- 特征必须只使用预测时刻可获得的数据；标签窗口、观察窗口和时间切分应明确。
- 训练、验证、测试集宜按实体或时间隔离，防止同一实体交叉或未来信息泄漏。
- 对大规模数据做抽样、去重、缺失/异常统计和分布检查，不能只看任务 success。
- 输出数据集、特征或批量预测需带批次/模型版本，便于回退、对账和复现。

## 五、两个可实操作品 / 交付物

### 作品 A：可重跑的离线特征 / 指标作业

使用公开或合成数据实现一个 Spark SQL/DataFrame 作业：按日期读取原始数据，清洗、去重、Join 维度、聚合为特征或指标宽表。交付包括：

- 输入/输出 schema、实体粒度、分区策略、时间口径和数据字典。
- 作业提交参数、运行日志位置和不含敏感信息的环境说明。
- 质量校验：行数、去重、空值、范围、分区完整性和源/目标对账。
- 安全重跑设计：临时输出、批次 ID、成功标记、发布/回滚与重复运行验证。
- 一次性能观察：说明一个 Shuffle/分区/文件问题的证据、改动和复测结果。

### 作品 B：数据倾斜或小文件问题的诊断报告

构造有热点 key 或碎片文件的合成数据，运行基线作业，记录 Stage/Task、Shuffle、文件数和耗时。然后只做一个针对性改动（例如预聚合、拆热点或调整输出分区），比较前后结果正确性与运行证据。重点不是追求漂亮数值，而是让判断可复核、可回退。

## 六、高频面试题与考察点

| 问题 | 建议回答要点 |
| --- | --- |
| RDD 的 Transformation 与 Action 有什么区别？ | Transformation 构建惰性血缘，Action 触发实际执行；还应联系 DAG、Stage 和重复计算理解。 |
| 为什么 Spark 作业会发生 Shuffle？ | 宽依赖、按 key 聚合或 Join 通常需要跨分区重新分发；成本包含网络、排序、磁盘和任务同步。 |
| 数据倾斜如何定位和处理？ | 用 Task 时长/输入量、key 分布、执行计划确认；从业务 key、预聚合、热点拆分、分区策略等处理，验证结果正确性。 |
| 什么时候缓存？ | 多次复用且重算昂贵时；需评估内存、驱逐、序列化和 `unpersist`，不能机械缓存所有 DataFrame。 |
| Join 怎么避免结果膨胀？ | 明确两侧粒度和唯一键，先去重/过滤，再选择 Join 策略，并做行数和业务键对账。 |
| 作业成功如何证明数据正确？ | success 只表示执行完成；还要检验 schema、分区、行数、去重、空值、范围、源目标对账和业务抽样。 |
| 如何处理流式重复、迟到和故障恢复？ | 定义事件 ID、时间语义、watermark/状态/checkpoint、幂等输出和回放/对账；并说明当前环境实际支持的语义。 |
| Spark 如何支撑 AI 数据集构建？ | 规模化清洗、Join、聚合、特征/标签快照；重点保证时间边界、版本、切分、质量和可复现，而不是只强调算力。 |
