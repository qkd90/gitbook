# Go 开发：AI 与大数据招聘能力地图

## 使用范围

本目录当前没有独立主题文章，只有目录入口页给出的 Go 语言、并发、Web 服务和工程交付学习框架。因此本页不会把尚未存在的资料包装成已完成能力。

它的作用是把现有入口中的学习方向变成招聘准备清单：明确目标岗位需要什么、怎样做出可验证作品、哪些资料必须优先补齐。

## 岗位关联

### AI 应用与基础设施后端

- Go 常用于高并发 API、模型网关、任务执行器、数据接入、运维工具和云原生服务。目录入口已经把并发、context、Web 服务、日志、数据库和 Docker 列为核心方向。
- 对 AI 应用岗位而言，语言选择不是卖点；真正需要说明的是请求超时、取消、并发上限、流式/长耗时连接、外部依赖失败和资源回收。
- 目前本目录没有模型调用、流式协议、鉴权或观测样例，因此这些只能作为待补齐能力，不能写成“已掌握项目经验”。

### 大数据与实时数据工程

- Go 可以承担数据采集、轻量 ETL、消息消费、指标聚合、批处理工具和服务端数据接口，但当前目录尚无 Kafka、列式存储或数据处理代码资料。
- 面试准备应把 Go 的 goroutine、channel、context 和 sync 转化为对数据并发、背压、取消和资源泄露的解释，而不是只背语法。
- 真正的流处理、批处理和数据仓库能力仍需与 Hadoop、Hive、Spark、Flink、数据库目录联动补齐。

### 后端平台与云原生服务

- Go 适合构建小而清晰的服务、命令行工具和运维组件。当前入口页已明确项目结构、配置、日志、测试、数据库访问和 Docker 是工程交付路径。
- 招聘中会追问：模块怎么拆、错误怎么传递、请求为什么会泄露 goroutine、如何停机、如何压测和如何观察。当前目录需尽快补这些运行证据。

## 可实操项目与交付物

### 项目一：可取消的数据接入服务

项目目标是实现一个模拟数据接入 API，重点证明 context、并发控制和错误处理，而不是伪造“高吞吐生产系统”。

- 接口接收少量模拟事件，校验字段、时间和唯一标识后投递给内部处理队列。
- 用 context 传递请求取消和截止时间；禁止在业务链路中随意改用 background context 切断取消信号。
- 使用有界 worker 数量，明确队列满、请求取消、处理失败和服务关闭时的行为。
- 每个 goroutine 都要有退出路径；用日志或测试证明服务关闭后不会继续积压任务。
- 对重复事件设计幂等依据；如果只实现内存去重，要说明重启或多实例后的限制。
- 将输入、处理结果和错误分开记录，日志中不输出原始敏感载荷。

建议交付物：

- 并发模型图，说明生产者、队列、worker、取消信号和关闭顺序。
- 接口契约、状态码/错误响应样例和至少十个边界测试。
- 并发测试记录，至少覆盖超时、取消、队列满、重复事件和服务关闭。
- 一份资源风险说明，明确没有做的持久化、分布式协调和容量验证。

### 项目二：面向 AI 调用的轻量任务网关

项目目标是用模拟模型执行器体现长耗时请求的工程边界。没有可信的模型服务时，固定返回或延迟模拟即可。

- 定义提交任务、查询任务和取消任务接口，区分同步等待与异步状态查询两种模式。
- 将外部执行器封装为接口，方便在测试中替换为成功、超时、格式错误和部分成功的模拟实现。
- 为每次调用设置 deadline，并明确哪些错误可重试、最大重试次数和为什么必须有幂等标识。
- 记录任务标识、请求标识、耗时、结果状态和错误类别；不记录用户输入全文、令牌或内部地址。
- 对调用方断开、执行器慢、执行器重复回调、服务重启等情形定义可观察行为。
- 如果未实现流式响应、限流、鉴权、分布式存储或真实模型协议，应在 README 中列为明确限制。

建议交付物：

- 服务模块图、执行器接口、任务状态机和失败矩阵。
- 可替换的 mock 执行器及其测试，避免测试依赖外网或真实模型。
- 一份运行说明，包含 Go 版本、构建/测试命令、配置项和本地验证步骤。

### 项目三：数据质量命令行检查工具

项目目标是展示 Go 在后端平台和数据工程周边工具中的适用性。

- 读取本地 CSV 或 JSON 小样本，检查必填字段、时间格式、重复主键、数值范围和异常行数。
- 命令行参数明确输入路径、规则文件路径、输出路径和失败阈值；路径与错误要可定位。
- 输出机器可读的结果摘要和人工可读的错误样例，限制输出条数避免日志爆炸。
- 规则和数据均使用合成样例，不放真实用户、业务或医疗数据。
- 用不同大小、空文件、乱码、非法时间和重复记录验证失败路径。

## 达标判断

在本目录资料补齐前，可以用以下标准避免“写过一段 Go”被误当成“已具备服务交付能力”。

- 能独立说明每个 goroutine 从哪里启动、由谁等待、何时退出，以及异常如何返回。
- 能为每个 channel 说明发送方、接收方、关闭方和缓冲容量，而不是靠试运行消除阻塞。
- 能将 context 从 HTTP 请求传到执行器和数据访问边界，并用测试验证取消会停止工作。
- 能从零启动一个小服务，写出配置、日志、测试和构建说明，而不是只贴 main 函数。
- 能说明服务重启、多实例、队列满和外部依赖失败时当前实现的真实限制。
- 能给出竞态检测或并发测试结果；没有运行就不宣称 goroutine 安全。

建议先将项目一做到可测试，再复用其取消、日志和错误边界完成项目二；项目三最后加入。这样能避免一开始同时引入网络、并发、数据格式和外部依赖，导致无法判断错误来自哪里。

每完成一项，都应记录一次失败用例和一次修复用例，形成可在面试中讲清的工程复盘。

若项目只在单机内存运行，也要在文档中明确标注。这并不降低练习价值，但能避免把单机语义误说成分布式可靠性。

面试时应主动先说明这一边界，再说明下一步会用持久化、幂等键和观测能力怎样补齐。

## 简历与面试表达

### 简历写法

当前目录尚无已有实现可直接作为项目经历。完成上述项目后，可以用以下结构表达，并用真实数据替换任何占位符。

- 用 Go 构建可取消的数据接入服务，设计有界 worker、context deadline、重复事件处理和关闭流程，并以边界测试验证退出行为。
- 实现模拟 AI 任务网关，将执行器调用与任务状态分离，覆盖超时、取消、格式异常和重复回调等失败路径。
- 开发数据质量命令行工具，输出字段校验、重复检测和异常样例；明确适用的数据格式和未覆盖的规模限制。
- 按既有 Go 项目分层、日志和错误处理约定完成局部服务改动，保留编译/测试与差异检查证据。

### 面试考察点

1. slice 和 map 的零值、扩容和并发访问分别有什么风险？什么时候要复制而不是直接共享？
2. Go 接口为什么是隐式实现？它如何帮助测试替身和执行器抽象，又有哪些过度抽象风险？
3. goroutine 泄露通常由什么造成？如何设计取消、channel 关闭和 worker 退出顺序？
4. context 应该在调用链中怎样传递？为什么不应为了方便改用 background context？
5. channel 和 mutex 分别适合解决通信还是共享状态问题？什么时候会造成死锁或阻塞放大？
6. 一个外部 AI 调用设置超时后，为什么还需要幂等、状态查询和结果审计？
7. Go 服务如何优雅退出？正在处理的任务、等待中的请求和日志/连接资源怎样处置？
8. 如何验证并发服务没有数据竞争？竞态检测、单元测试和压力测试各覆盖什么？
9. 如果接入 Kafka 或数据库，如何保证一次处理不会因为重试变成重复写入？

## AI 协作方法

Go 代码短小但并发错误隐蔽。AI 适合做并发设计审查和测试枚举，不应被当作 goroutine 生命周期的最终裁判。

1. 先把 goroutine 所有者、输入 channel、退出条件、context、队列容量和错误返回方式画出来，再让 AI 审查。
2. 要求 AI 对每个并发方案列出泄露、死锁、竞态、无限重试和阻塞放大的反例。
3. 用 AI 生成 table-driven test 的测试表草稿，再自行核验期望值和资源释放。
4. 对外部服务调用要求 AI 显式说明 deadline、重试上限、幂等键和失败后的调用方行为。
5. 生成代码必须经过 gofmt、编译、单元测试和竞态检查；没有运行证据就不能声称并发安全。
6. 不把生产配置、访问 Token、真实用户载荷、私有仓库内容或内部错误日志粘贴给 AI。
