# AI 与大数据招聘能力地图

> 本页以本目录现有的 [数仓项目入口](README.md) 和 [项目架构图](项目架构图.png) 为依据。架构图展示的是一条离线与实时并行的参考链路；当前目录尚未保存具体建表 SQL、任务代码或生产运行数据，因此简历和面试中应把“理解/设计”与“已实现/已上线”明确区分。

## 一、岗位定位：这是最直接的数据工程作品集骨架

本目录连接业务系统、日志、离线数仓、实时计算、调度、可视化和数据接口，是面向大数据工程师、数仓开发、实时数仓、数据平台和 AI 数据工程岗位最重要的材料之一。

| 岗位方向 | 架构图中的对应能力 | 可向 AI 方向延伸的价值 | 仍需补齐的核心证据 |
| --- | --- | --- | --- |
| 数仓开发工程师 | ODS、DIM、DWD、DWS、ADS 分层；主题域、指标和报表 | 为模型训练/分析提供可信历史数据 | DDL/DML、分区/主键、指标口径、调度与对账结果 |
| 大数据开发工程师 | DataX、Maxwell、Flume、Kafka、Hadoop、Hive/Spark、Flink | 离线+实时采集、处理、存储和服务化 | 可运行作业、数据量、性能、异常处理和发布记录 |
| 实时数仓工程师 | Kafka、Flink、Phoenix/HBase、Redis、ClickHouse、实时接口 | 实时特征、实时画像、在线指标与异常事件 | 时间语义、幂等、维度更新、乱序/迟到与压测证据 |
| 数据平台工程师 | DolphinScheduler、ZooKeeper、质量、血缘、权限、告警 | 为算法/BI/业务团队提供可用数据资产 | 多租户、权限、监控、CI/CD、元数据和运维治理 |
| AI 数据/特征工程师 | 原始事件—明细—汇总—服务链路 | 训练样本、标签、离线特征、在线特征的一致性 | 特征版本、训练/推理一致性、泄漏检查和模型评估 |

**招聘定位建议：**不把“会一堆组件”作为主线，而是围绕一个指标或数据产品，讲清从源头、分层、计算、质量、服务到消费端的完整责任。

## 二、从现有架构图抽取的能力地图

```text
数据采集与数据服务闭环
├─ 数据源与入口
│  ├─ Web/App → Nginx → Spring Boot → MySQL 业务数据
│  ├─ 业务全量：DataX → Hadoop
│  ├─ 业务增量：Maxwell → Kafka
│  └─ 行为日志：Nginx/日志服务/文件 → Flume → Kafka
├─ 离线数仓
│  ├─ ODS：保留原始事实与可追溯性
│  ├─ DIM：统一维度、主键与历史变化规则
│  ├─ DWD：统一明细粒度、去重和业务语义
│  ├─ DWS：按主题汇总、服务公共指标
│  └─ ADS：面向看板/接口的应用数据
├─ 实时数仓
│  ├─ Kafka 事件流 → Flink 实时处理
│  ├─ 实时 ODS/DWD、维度查询和旁路缓存
│  ├─ Phoenix + HBase、Redis、ClickHouse 宽表
│  └─ Spring Boot 数据接口 → Sugar 等实时展示
├─ 编排、协调和治理
│  ├─ DolphinScheduler：DAG、依赖、补数、失败重试、告警
│  ├─ ZooKeeper：分布式协调
│  ├─ 数据质量：空值、重复、波动、主外键一致性
│  └─ 权限、脱敏、审计、血缘、负责人和下线
└─ 消费与验证
   ├─ DataX → 结果 MySQL → Superset 离线看板
   ├─ 数据接口、报表、运营分析和算法特征
   └─ 源数据、离线结果、实时结果三方对账
```

这张图的关键不是把 DataX、Maxwell、Flume、Kafka、Flink、ClickHouse 等名词罗列出来，而是说明每个边界的 **主键、增量标识、延迟、重复、失败重试、血缘和消费契约** 是什么。任何一段未定义，这条链路都无法稳定成为数据资产。

## 四、可交付实战项目

### 项目一：离线 + 实时统一口径的用户活跃数据产品

**场景：**使用合成的用户访问和业务事件，实现一个“日活/近 5 分钟活跃数”数据产品。它对应架构图中日志采集、Kafka、Flink、ODS/DWD/DWS/ADS、结果库和看板的完整骨架。

```text
模拟 Web/App 行为日志
  ├─ 离线：文件/批数据 → ODS → DWD 去重 → DWS/ADS 日活
  └─ 实时：Kafka → Flink → 实时明细/宽表 → 查询结果
                         ↓
                    离线/实时口径对账
```

**必须交付：**

- 数据源台账：`event_id`、`user_id`、`event_time`、事件名、采集时间、分区字段、脱敏规则和保留周期。
- ODS、DWD、DWS、ADS 的表设计：每层粒度、主键、业务日期、去重策略、是否允许更新和下游消费者。
- 一张指标口径卡：日活的活跃事件定义、时区、去重键、迟到/补数处理、筛选条件和负责人。
- 一份实时作业与一份离线汇总脚本/SQL；输出同一天的结果和差异解释。
- 质量检查：空主键、重复 `event_id`、未来时间、异常波动、维度缺失以及数据延迟。

**验收方法：**同一批固定模拟事件可以重跑；离线和实时口径差异有阈值和归因；任一异常数据都有审计去向，而不是悄悄被丢弃。

### 项目二：订单/设备主题域的增量采集、维度拉链与补数演练

**场景：**围绕一张业务事实表和一张会变更的维表，模拟“每日全量 + 实时增量”或“全量初始化 + CDC 增量”的数据进入数仓。可用匿名订单、设备或内容数据，避免真实业务信息。

**必须交付：**

- 源表到目标表字段映射，明确源主键、更新时间、删除标识和增量水位。
- 全量/增量切换策略：首次初始化、断点恢复、重复投递、晚到更新和失败重跑如何处理。
- 维表历史规则：快照、拉链或覆盖更新的选择依据；事实表关联的是哪个时间版本的维度。
- DolphinScheduler 风格的 DAG：依赖、重试、告警、分区补数范围和回滚流程。
- 对账 SQL/脚本：源表行数、主键覆盖、关键金额/数量、维度关联命中率和重复率。

**验收方法：**模拟一条更新、删除、重复和跨天晚到记录，说明最终 DWD/DWS 哪些分区/记录变化、为什么变化、如何避免重复。

### 项目三：面向 AI 的离在线特征一致性检查

**场景：**选择一个简单的匿名实体特征，例如“过去 7 天行为次数、最近一次行为距今天数、近 30 分钟活跃数”，一份由离线层生成，一份由实时层生成。

**必须交付：**

- 特征定义、时间参考点、实体主键、空值默认、版本号、训练集使用范围和线上服务使用范围。
- 离线脚本/SQL、实时计算逻辑、样例输入输出和逐字段对账结果。
- 泄漏检查：任何标签之后才发生的事件不得进入训练特征；训练/验证/测试按实体和时间正确切分。
- 差异归因清单：时区、窗口关闭、迟到、CDC 延迟、维表更新、去重和补数。

这个项目可让数仓经验自然连接 AI 数据工程，但不能据此宣称模型效果已经验证；特征正确性、训练过程和模型评估仍需要独立证据。

## 五、简历表达：从组件堆叠改为数据责任

| 可写主题 | 推荐的证据化表述 | 面试中应拿出的材料 |
| --- | --- | --- |
| 数仓分层 | “按 ODS—DIM—DWD—DWS—ADS 设计主题域数据模型，明确每层粒度、主键、分区、保留和下游消费。” | 表模型、血缘图、字段/指标字典 |
| 数据采集 | “为全量、增量和日志事件分别定义采集方式、水位、去重和重跑策略。” | 源表台账、CDC/文件样例、失败重试流程 |
| 实时处理 | “使用 Kafka/Flink 处理事件流，围绕事件时间、主键、窗口、幂等与延迟输出实时指标。” | 固定事件样例、窗口结果、作业配置 |
| 质量与对账 | “建立空值、重复、波动、主外键一致性和实时/离线对账规则，输出问题明细与归因。” | 质量规则、阈值、对账 SQL、告警样例 |
| 数据服务 | “将 ADS/实时结果以结果库、接口或看板方式交付，标注刷新频率、延迟、权限和字段契约。” | API/看板截图、刷新说明、权限模型 |
| AI 数据衔接 | “为模型/特征需求定义训练与线上数据的主键、时间边界、版本和一致性校验。” | 特征定义、对账报告、泄漏检查 |

不要写“搭建千万级实时数仓”或“日处理 xx 亿数据”，除非有真实集群、监控和本人职责证据。一个可重跑、可对账、可解释的小项目，比无法证实的数字更适合校招/转型招聘。

## 六、面试要点：必须能讲清的核心问题

1. **为什么要分 ODS、DWD、DWS、ADS？**
   - 说明原始可追溯、明细语义统一、主题汇总复用和应用交付分别解决什么问题，不能只背层名。
2. **全量同步、CDC 增量和日志采集有什么不同？**
   - 全量解决初始/覆盖数据，CDC 关注变更顺序和删除，日志关注事件 schema/重复/迟到；三者的水位和重跑策略不同。
3. **如何设计一个指标口径？**
   - 给出名称、业务定义、粒度、主键、时间/时区、过滤条件、去重、维度、计算公式、刷新频率、负责人和变更流程。
4. **实时与离线结果不一致怎么排查？**
   - 先对齐时间范围/时区和主键，再检查采集延迟、窗口、去重、维度更新、补数和 Sink；用样例记录定位，不凭感觉改口径。
5. **为什么数据质量不能只看行数？**
   - 行数相同仍可能主键重复、字段错位、金额错误、维表缺失或时间异常；需要完整性、唯一性、准确性、及时性和一致性规则。
6. **维度表变更如何影响事实和指标？**
   - 要解释覆盖、快照、拉链的取舍，以及事实关联哪个时间版本；否则历史报表会被新属性重写。
7. **怎样做补数才安全？**
   - 明确分区范围、依赖、幂等、回滚、重跑顺序和对账，不能在未知范围直接覆盖线上结果。
8. **AI 特征为什么要做离在线一致性检查？**
   - 同名特征因窗口、时区、延迟和维表版本不同可能不一致，训练/线上偏差会直接损害模型效果。
9. **如何保护数据安全？**
   - 分级分类、最小权限、脱敏、审计、保存期限和导出限制；测试使用匿名/合成数据。

## 七、AI 协作方式：用于加速资料整理与质量设计

AI 可以帮助从字段说明生成数据字典草案、检查建表字段映射、列出质量规则、生成匿名测试事件、整理 DAG 依赖、比较实时/离线口径和起草复盘。人工必须确认真实业务定义、主键、时间字段、权限、生产 SQL 的作用范围、调度窗口和最终数据质量结论。

```text
请协助评审一个数据链路设计，先不要生成生产 SQL。
数据源：<表/日志及匿名字段>；主键：<字段>；增量依据：<时间/CDC 位点>；
目标：<ODS/DWD/DWS/ADS 或实时指标>；消费者：<看板/API/模型>。
请输出：分层粒度、去重/晚到/删除规则、质量校验、调度依赖、
离线实时对账点和需要人工确认的业务语义。不得臆造字段、数据量或指标口径。
```

AI 生成的 SQL、DDL 或数据血缘图都要在匿名环境用小样本执行和对账。对生产库的写入、删除、分区覆盖和权限变更必须人工审查。

## 八、现有资料缺口与下一步

| 当前缺口 | 为什么影响招聘可信度 | 优先补充的产物 |
| --- | --- | --- |
| 仅有架构图和说明，缺少主题域表模型 | 看不出候选人能否落到字段、主键和粒度 | 一个匿名主题域的 ODS/DWD/DWS/ADS DDL 与字段字典 |
| 缺少 DataX/Maxwell/Flume/Kafka/Flink 的实际配置 | 无法验证采集与异常处理能力 | 合成数据的配置、启动方式、失败/重跑记录 |
| 缺少调度 DAG 和补数实操 | 数仓岗位常考依赖、分区、重跑和回滚 | 一份可演示 DAG、补数范围及对账流程 |
| 缺少质量/血缘/权限系统化材料 | 数据平台岗位不只关心计算 | 规则表、告警样例、责任人、血缘图和脱敏策略 |
| 缺少结果服务及性能证据 | 无法说明数据怎样被真正使用 | 小看板/API、刷新延迟、查询耗时和权限说明 |
| 缺少 AI 数据契约案例 | 无法凸显向 AI 数据工程转型的差异化 | 离在线特征对账、泄漏检查、特征版本说明 |

## 九、投递前自查

- 能用一张图讲清业务数据、日志数据、离线和实时链路的入口、处理、存储和出口。
- 能拿出至少一个指标口径卡、一张分层表模型、一组质量规则和一次对账结果。
- 对“全量、增量、补数、重跑、删除、迟到、幂等”均有具体处理方案。
- 清楚区分架构图参考、个人实操、测试验证和生产运行四类事实。
- 能说明数仓如何为 AI 提供可信训练/特征数据，但不把数据链路等同于模型研发。
