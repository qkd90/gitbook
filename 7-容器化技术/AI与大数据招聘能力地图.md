# 容器化技术：AI 与大数据招聘能力地图

容器化是 AI 平台和大数据平台把“本地可运行”变成“环境可复现、集群可调度、版本可回退”的关键能力。本目录的 Docker、Compose、Kubernetes 和排障材料，适合沉淀为 MLOps、数据平台工程、云原生后端或运维开发的招聘作品。

> 招聘中不应把 Kubernetes 描述成“会敲 kubectl”。真正可被考察的是：能否把应用、依赖、配置、资源、数据、发布和故障恢复的边界声明清楚。

## 一、岗位定位与能力信号

| 目标岗位 | 招聘方关注的问题 | 能展示的容器化能力 | AI / 大数据关联 |
| --- | --- | --- | --- |
| MLOps / AI 平台工程 | 模型服务怎样稳定交付和扩缩容 | 镜像、配置、探针、灰度、资源与回滚 | 模型镜像与权重分离、推理版本可追溯、GPU/显存需求需额外验证 |
| 数据平台工程 | 批作业、流作业和依赖服务怎样部署 | 集群对象、网络、存储、日志和资源配额 | Spark/Flink/Hadoop 任务与元数据、消息、对象存储的运行边界 |
| 云原生后端 | 服务如何从本地到集群交付 | Dockerfile、Compose、Deployment、Service、Ingress | API、特征服务、数据服务的健康检查和可观测性 |
| SRE / 运维开发 | 故障怎样缩小范围并恢复 | Events、日志、Service/Endpoints、资源和发布记录 | 区分 Pod 异常、节点资源、依赖服务、配置和数据卷问题 |
| 测试开发 | 多服务环境怎样可重复搭建 | Compose 环境、环境变量模板、接口验证 | 用合成数据验证数据接口、模型接口和异步任务链路 |

## 二、从代码到可运行服务的完整链路

```text
源码 + 依赖清单
        │
        ├─ Dockerfile / .dockerignore ──> 可追溯镜像标签
        │
        ├─ Compose ─────────────────────> 本地多服务联调
        │
        ├─ 配置与密钥 ──────────────────> ConfigMap / Secret 或受控配置系统
        │
        ├─ Kubernetes 声明 ─────────────> Deployment / Service / Ingress / PVC
        │
        ├─ 运行保障 ────────────────────> 探针、日志、requests/limits、监控
        │
        └─ 发布治理 ────────────────────> 版本、灰度、回滚、变更记录、复盘
```

面试回答应顺着这条链路说明“谁负责什么”：镜像只封装可运行的应用和依赖，环境差异放在配置，持久数据放到受管存储/明确的数据卷，运行状态和发布证据在集群侧可观察，任何临时登录容器的修改都不能代替正式交付。

## 三、核心能力拆解

### 1. Docker：可复现构建而不是只会 `docker run`

| 能力点 | 应说清的决策 | 可验证交付物 |
| --- | --- | --- |
| 镜像构建 | 基础镜像、工作目录、依赖安装、启动命令、构建上下文 | Dockerfile、.dockerignore、构建命令和镜像标签规则 |
| 镜像体积与安全 | 多阶段构建、最小运行时依赖、非 root 运行、漏洞扫描流程 | 构建说明和不含敏感信息的镜像检查记录 |
| 配置分离 | 端口、依赖地址、日志级别、运行参数不写死在镜像里 | 环境变量模板、配置项说明、Secret 注入方式 |
| 容器运行 | 网络、端口、数据卷、重启策略、日志输出 | `docker compose` 或运行命令、启动/停止/排查手册 |

现有资料可从 [Docker](1-docker/README.md)、[docker 入门](1-docker/docker入门.md)、[docker-compose](1-docker/docker-compose.md) 与 [Python 项目 docker 部署](1-docker/python项目docker部署.md) 开始。

### 2. Compose：本地联调与可重复测试环境

对 AI 与数据服务，Compose 的价值是把 API、数据库、缓存、消息队列、对象存储或 mock 数据源放进同一个可重复的环境。一个合格的 Compose 文件至少应解释：

1. 服务之间通过什么网络名访问，而不是靠本机 IP 假设。
2. 哪些数据需要挂载卷，卷的初始化和清理规则是什么。
3. 配置从哪里注入，示例中是否避免了真实账号与 Token。
4. 启动依赖是“容器已启动”还是“服务已就绪”，后者要配合健康检查或应用重试。
5. 测试如何重置状态，避免一次测试的历史数据污染下一次结果。

### 3. Kubernetes：对象关系与运行语义

| 对象 | 要解决的问题 | 招聘中常见追问 |
| --- | --- | --- |
| Pod / Deployment | 如何定义运行单元、版本和副本 | Pod 为什么会重启？滚动更新如何避免中断？ |
| Service / Endpoints | 如何发现后端并获得稳定访问入口 | Service 有了为何仍不可达？Endpoints 为空说明什么？ |
| Ingress | 如何让外部流量进入服务 | 路径、域名、TLS、后端端口和控制器分别在哪一层验证？ |
| ConfigMap / Secret | 如何把配置与镜像分离 | 配置更新为何未生效？密钥如何避免进入镜像和 Git？ |
| PVC / 存储 | 如何让有状态数据跨 Pod 生命周期保存 | 哪些数据可放卷，哪些应进入受管数据库/对象存储？ |
| requests / limits | 如何约束和调度资源 | CPU/内存限制不合适会带来什么启动、驱逐或性能问题？ |
| liveness / readiness | 如何区分进程存活与可接流量 | 探针错误会怎样放大故障？依赖未就绪时如何设计？ |

学习时配合 [Kubernetes 基础概念](2-k8s云原生实战/Kubernetes基础概念.md)、[Kubernetes 核心实战](2-k8s云原生实战/Kubernetes核心实战.md) 和 [排查 K8s 问题](2-k8s云原生实战/排查k8s问题.md)。

### 4. AI / 大数据工作负载的特殊边界

容器化知识在 AI、大数据场景必须补足以下判断，而不是机械复用普通 Web 服务模板：

- **训练、批处理和在线推理不是同一种负载**：前两类常看吞吐、队列、可重试和数据落盘；在线推理看延迟、并发、模型加载和回退。
- **镜像、权重和数据要分离**：模型权重、训练数据、特征和输出通常不应被写入镜像层；需要明确挂载、对象存储或模型仓库的版本/权限约定。
- **资源不能只填默认值**：CPU、内存、磁盘、网络及 GPU/显存必须基于实际压测或运行证据设置。GPU 调度和多卡训练不在本目录现有材料范围内，不能仅凭 Kubernetes 基础知识宣称熟练。
- **有状态服务需谨慎**：消息、数据库、元数据、检查点与任务输出的持久化、备份、升级和恢复必须独立设计。
- **发布需兼顾数据契约**：镜像成功启动不代表模型/数据版本兼容；上线验证还要检查 schema、特征顺序、任务输出和下游消费。

## 四、两个可实操作品 / 交付物

### 作品 A：本地数据服务联调环境

使用任意一个不含真实数据的小型 API，配套一个数据库或缓存，完成 Dockerfile 与 Compose：

- 镜像按版本标签构建，`.dockerignore` 排除构建产物、密钥和本地数据。
- Compose 中声明服务网络、持久卷、环境变量模板、健康检查和日志查看命令。
- 提供初始化、启动、接口验证、停止和数据清理脚本说明。
- 设计两组测试：正常数据流与依赖不可用/错误配置流。

交付时展示结构、命令、测试结果和失败时的定位过程；不展示真实连接串或生产数据。

### 作品 B：Kubernetes 发布与故障演练包

为同一个服务提供 Deployment、Service、Ingress、ConfigMap/Secret、资源限制和探针。至少演练两种异常：镜像版本回退、`CrashLoopBackOff`、`readiness` 失败、Service 无 Endpoints 或配置未生效。每次演练按 `describe → events → logs → Service/Endpoints → Ingress/DNS → 依赖` 记录证据和恢复动作。可先参考 [CrashLoopBackOff 排查](2-k8s云原生实战/k8s创建容器报错CrashLoopBackOff.md)。

## 五、高频面试题与考察点

| 问题 | 回答的关键判断 |
| --- | --- |
| Docker 镜像和容器有什么区别？ | 镜像是不可变构建产物，容器是运行实例；配置、数据卷和运行状态不应混进镜像。 |
| 为什么本地 `docker compose up` 成功，集群仍失败？ | 检查镜像、配置、DNS/Service、权限、资源、探针、存储和入口层差异；不要假设“环境等价”。 |
| Pod 出现 `CrashLoopBackOff` 怎么办？ | 先看退出原因、事件和日志；再核对启动命令、环境变量、挂载、端口、资源与依赖；修复后验证探针和业务接口。 |
| readiness 与 liveness 怎样区分？ | readiness 决定是否接流量，liveness 判断是否需要重启；误配会造成流量打到未就绪实例或无意义重启。 |
| Service 正常但访问不到后端，排查顺序？ | 选择器与标签、Endpoints、目标端口、Pod 就绪、网络策略/DNS、Ingress/网关路径与 TLS。 |
| 怎样发布 AI 模型服务？ | 版本化镜像/模型/配置，分离权重与密钥，定义资源与探针，做灰度和输入输出契约校验，观察延迟错误率和版本回退能力。 |
| 容器化如何处理数据持久化？ | 区分临时缓存、检查点、业务数据和模型/训练数据；选择卷、数据库或对象存储，并定义备份、权限和生命周期。 |

## 六、简历证据与自我评估

可以把项目描述写成“场景—方案—验证—边界”，例如：

> 为多服务联调环境编写 Dockerfile 与 Compose，分离镜像、环境配置和持久卷；为服务补充健康检查、接口集合和依赖异常演练，并形成启动、回滚和排查文档。实际使用的技术、范围和结果应以可展示记录为准，未压测的性能不写成结论。

自查清单：

- [ ] 能解释镜像层、配置、容器数据和持久化之间的边界。
- [ ] 有一个可在新机器复现的 Compose 项目和不含密钥的配置模板。
- [ ] 能画出 Deployment、Service、Ingress、ConfigMap/Secret、PVC 的关系。
- [ ] 能复盘一次 Pod/网络/配置故障，给出原始证据而不是只有结论。
- [ ] 能说明 AI/大数据任务的资源、数据版本和输出幂等与普通 Web 服务的差异。
