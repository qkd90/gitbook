# 开发框架和工具：AI 与大数据招聘能力地图

## 使用范围

本页把本目录的 Spring Boot、工程结构、接口治理、数据访问、日志、协作与环境配置资料，整理为 AI 应用后端、大数据平台服务和企业后端平台岗位可验证的工程能力。

这里的重点不是罗列注解或依赖，而是说明一个服务从本地启动、接口设计、数据访问、异常处理到发布排查如何形成闭环。

## 岗位关联

### AI 应用后端

- AI 应用通常需要把模型、检索、工作流或异步任务包成对内对外稳定的服务；Spring Boot 配置、Bean 管理、统一异常和拦截器资料对应这层服务治理。
- 模型服务的调用结果可能失败、超时或部分成功。候选人应能把这些业务状态和系统异常区分开，而不是只返回一个笼统的失败提示。
- 任务、知识库、会话、审计和权限常属于普通后端能力。MongoTemplate、MyBatis-Plus、数据权限和租户资料可用于形成可信的数据边界说明。

### 大数据平台服务

- 数据平台除了离线或实时计算任务，还需要元数据、任务配置、权限、运行记录、告警和管理后台。当前目录的项目结构、环境配置、异常处理、日志和租户能力正是这类控制面的基础。
- 面试官往往会追问一个任务提交接口怎样做参数校验、环境隔离、日志检索和异常归因。只会写 Controller 不足以回答。
- 此目录不直接替代 Spark、Flink 或数仓知识；它解决的是如何把这些计算能力组织成可维护的业务服务。

### 后端平台与中台

- 平台岗位最重视团队可维护性：模块职责、配置管理、统一返回、身份校验、数据权限、日志规范、分支协作和发布过程都必须说清。
- 这些能力同样是 AI 系统从演示走向多人使用的前提，尤其要避免模型调用、业务事务和权限控制混在一个长方法中。

## 能力分层与证据

| 层级 | 要解决的工程问题 | 本目录资料基础 | 可向面试官展示的证据 |
| --- | --- | --- | --- |
| L1 本地可运行 | 新机器如何启动、依赖如何解析、配置在哪里 | IDEA、Maven、Spring Boot 配置 | 启动说明、环境变量清单、无敏感值配置样例 |
| L2 结构可维护 | Controller、Service、数据访问、配置类如何分工 | 项目结构设计、代码优化技巧、Bean 注解 | 模块图、一次职责拆分说明、代码审查记录 |
| L3 接口可治理 | 参数、鉴权、统一返回和异常如何一致 | 统一异常、拦截器、代码优化 | 接口契约、错误码表、非法请求测试 |
| L4 数据可隔离 | 多租户、数据权限和数据访问如何不串数据 | 数据权限和租户、MongoTemplate、MyBatis-Plus | 权限矩阵、过滤条件说明、越权测试 |
| L5 配置可发布 | 开发、测试、生产怎样隔离，变更怎样回退 | Maven Profile、配置文件、Git/GitLab | 配置分层示例、发布检查清单、回退策略 |
| L6 问题可定位 | 失败时怎样从日志和上下文定位 | Logback、Log4j2 与 Slf4j | 日志字段定义、一次异常定位链路、脱敏规则 |
| L7 AI 集成边界 | 模型结果、任务状态和业务数据怎样不混淆 | 由上述能力组合形成，目录内尚无完整模型接入样例 | 服务边界图、调用失败矩阵、补齐计划 |

L1 至 L3 是后端入职后能安全改服务的基本盘。AI 应用和数据平台岗位会继续看 L4 至 L7：是否知道权限、环境、可观测性和外部依赖的风险。

## 可实操项目与交付物

### 项目一：多租户 AI 任务管理服务

项目目标是证明你能把“模型能力”放进企业服务边界。可以使用假的模型调用器或固定结果，重点验证服务架构，而不是伪造模型效果。

- 定义租户、用户、任务、任务版本和运行记录五类核心对象，先画出数据归属和访问关系。
- 设计创建任务、查询任务、查看运行记录三个接口，指定谁能看全量、谁只能看本人或本租户。
- 按项目结构将接口、业务服务、数据访问、异常处理和配置分开；不要在控制器中直接写复杂查询或权限拼接。
- 用统一异常将参数错误、资源不存在、无权限、外部调用失败、内部异常分开返回。
- 用拦截器或现有鉴权上下文承接调用方身份；必须说明鉴权本身是否只是演示，以及生产系统还需要的认证机制。
- 用配置文件管理外部调用地址、开关和超时等非敏感示例值，并准备开发/测试两个环境的覆盖样例。

建议交付物：

- 模块图、接口清单、权限矩阵和状态说明。
- 配置样例与启动说明，所有密钥、令牌和地址使用占位符。
- 至少一组跨租户访问失败的接口测试，以及一组外部调用失败的错误返回测试。
- 一份日志字段约定，包含请求标识、租户标识、任务标识和错误类型，不输出原始敏感内容。

### 项目二：数据任务控制面 API

项目目标是模拟数据平台中的“提交任务、查状态、查执行记录”控制面，而不是在本项目中实现实际 Spark/Flink 作业。

- 设计任务模板、任务实例、参数版本和运行记录，区分配置变更与一次运行结果。
- 为任务提交增加字段校验：参数必填、时间范围、重复提交、非法状态和无权限访问。
- 用 Profile 或配置文件展示开发/测试环境差异，说明真正的生产配置不会提交到 Git。
- 将执行器调用抽成明确边界，调用失败时记录可定位上下文，避免用吞异常的方式让任务一直显示处理中。
- 把查询结果分页、排序、空值和异常状态写入接口契约；如果当前资料未覆盖分页实现，要在 README 中标出补充项。

建议交付物：

- 任务状态机、接口契约、异常码和运行日志样例。
- 一份“提交成功但执行失败”的链路说明，分别写清接口返回、运行记录和日志如何表现。
- 使用模拟执行器的单元/集成测试，不依赖真实生产任务或数据库。

### 项目三：后端工程体检清单

这是一份可直接在现有 Java 服务中使用的工程作品，适合作为没有完整新项目时的证明材料。

- 基于本目录资料建立结构、配置、异常、校验、日志、权限、数据访问、构建和协作九个检查维度。
- 选一个已脱敏或自建模块，逐项记录现状、风险、最小修改建议和验证方式。
- 不做大范围重构；重点展示如何读懂最近的同类实现、如何控制改动范围、如何防止环境配置泄露。
- 将发现的问题区分为代码问题、配置问题、权限问题和运行环境问题，避免所有风险都归因于框架。

## 项目验收清单

- 项目能在全新开发环境中按 README 启动，且启动步骤不依赖未说明的个人文件。
- 配置按环境拆分，示例中没有真实密码、令牌、客户标识和生产地址。
- 每个接口有成功、参数错误、无权限、资源不存在和系统异常的预期行为。
- Controller、Service、数据访问与横切能力的职责可以从目录结构和代码中直接看出。
- 数据权限测试至少覆盖同租户、跨租户和无身份上下文三种情况。
- 日志能串起请求、租户、任务和错误类型，同时不记录原始敏感输入。
- 交付说明把已实现、模拟实现、未实现和依赖外部环境的部分分开写。

如果项目需要接入模型或计算服务，验收还应增加依赖不可用、超时、重复回调和结果格式异常四类情形。框架代码写得整齐，并不代表外部依赖边界已经被验证。

准备展示时优先演示一次失败路径和定位过程，再展示正常接口；这更能说明工程能力。

## 简历与面试表达

### 简历写法

建议把“熟悉 Spring Boot”改写为可核验的交付动作。

- 按 Controller、Service、数据访问和统一异常边界组织后端模块，并提供接口契约与异常路径测试。
- 为任务或管理类服务设计环境配置、日志字段和发布检查清单，实际环境差异用真实情况填写。
- 在租户或数据权限场景中实现/验证过滤规则，保留越权访问用例而不是只写“实现权限控制”。
- 通过 Profile 区分开发与测试配置，避免将密钥、生产 URL 或个人令牌提交到版本库。

不要编造“高并发”“千万级”“提升百分比”。如果没有压测和线上证据，就写清功能范围、测试方式和仍未覆盖的部分。

### 面试考察点

1. 为什么 Controller 不应承载复杂业务和数据库访问？怎样判断一个方法应该下沉到 Service？
2. 统一异常与统一返回分别解决什么问题？业务异常、参数校验异常和系统异常如何区分？
3. 拦截器、Filter、AOP 各适合什么切入点？OPTIONS 请求为什么容易出问题？
4. 多租户或数据权限过滤放在哪里更可靠？怎样避免某个查询绕过过滤条件？
5. Spring Boot 的配置如何按环境覆盖？哪些值绝不能进代码库和日志？
6. @Resource 与 @Autowired 的使用差异是什么？在测试和替换依赖时要注意什么？
7. 远程模型或任务执行器失败时，接口、任务记录和日志各应该保留什么信息？
8. 你如何设计一个可排查的日志上下文，同时避免记录用户输入、密钥或隐私数据？

## AI 协作方法

AI 适合协助搭建骨架、枚举异常路径、生成测试初稿和审查重复代码；它不能替代对当前服务约定、配置来源和安全边界的核对。

1. 先把服务约束给全：JDK/Spring 版本、现有目录结构、接口格式、身份来源、数据库类型、允许改动范围。
2. 让 AI 先输出模块职责和接口字段表，再要求它列出不确定项，不直接让它一次性生成整个系统。
3. 对统一异常、拦截器、租户过滤等横切能力，要求 AI 说明执行顺序、异常传播和绕过风险。
4. 用 AI 生成参数错误、越权、空值、重复提交和外部服务失败的测试矩阵，再由开发者补项目实际场景。
5. 将生成代码与同模块最近的稳定实现逐行比较，核对依赖版本、注解语义、事务边界和日志格式。
6. 不上传真实配置、数据库导出、访问令牌、生产日志或客户数据；必要样例必须脱敏并缩小到最小范围。

## 当前资料缺口与补齐顺序

| 优先级 | 缺口 | 影响 | 建议补齐产出 |
| --- | --- | --- | --- |
| P0 | 单元测试、Mock、接口测试和测试数据管理 | 现有接口治理资料缺少可重复验证闭环 | 一个 Spring Boot 模块的测试分层示例 |
| P0 | 安全认证、授权模型、审计与敏感字段脱敏 | AI 和数据平台服务不能只靠演示级拦截器 | 身份链路图、权限矩阵、审计字段与越权测试 |
| P0 | 远程调用超时、重试、幂等、限流和熔断 | 外部模型/计算服务失败会直接影响稳定性 | 调用失败矩阵和最小可运行客户端示例 |
| P1 | API 文档、版本兼容、分页与异步任务 | 平台接口长期演进需要明确契约 | 接口版本策略和任务状态机案例 |
| P1 | CI/CD、制品、容器化和环境回滚 | 资料目前更多聚焦开发期 | 构建发布流水线与回滚检查清单 |
| P2 | 指标、链路追踪和容量验证 | 高阶平台岗位会追问运行证据 | 从请求到日志/指标的排查演练记录 |

补齐顺序应从 P0 的安全、测试和外部依赖稳定性开始。每一项都先完成一个小而可运行的服务案例，再扩展到复杂业务。
